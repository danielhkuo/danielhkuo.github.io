# Minimal terminal on phones: research (2026-11-19)

**Unpin the prompt and Safari anchors it.** Research report, 2026-11-19. Evidence for the design of the minimal
terminal page (`docs/superpowers/specs/2026-11-19-minimal-terminal-design.md`); it makes no product decisions.

The site owner's complaint about the terminal on a phone is that "the text bar just scrolls up so far that it blocks everything else from happening... It's not anchored onto like right above the actual keyboard part... instead it just kind of floats all over the place. It's a recurring problem." The evidence splits that complaint into two faults with different owners. The gap is Safari's: measured in the iOS 26.5 Simulator (iPhone 17e), in every layout tried, about **100 pt lies between the bottom of the visible page and the top of the keyboard**, filled by Safari's own address pill and form accessory bar, and WebKit's source forces that bar on for text inputs on an iPhone with an off switch only for embedding apps. On iOS 26, being anchored "right above the actual keyboard part" can therefore only mean sitting flush on top of Safari's bar. The floating is the page's: every layout that pinned the input, by CSS or by script, misplaced it at some point in the same probe (a sticky bar ended behind the keyboard after one drag, a locked `100dvh` shell was pushed 310 px up under the status bar, and a copy of the old terminal's method, a frame fitted to `visualViewport` by script, drew the input at the top of the visible area from stale readings before it jumped into place), while **the one layout that never misplaced it used no script at all: the input as the last element of an ordinary scrolling document**, which Safari itself scrolled to the bottom edge of the visible area. Existing projects point the same way: xterm.js's maintainers say mobile input is outside the library's scope, jQuery Terminal and the chat projects of September to November 2026 all chase `visualViewport` and report jumps, drift or a covered composer, and one such fix was reverted. The same structure answers the accessibility question, because a page whose content is headings, lists and links in the static HTML, with commands as real links and buttons, no autofocus and one short status message per command, is what screen readers, crawlers that do not run JavaScript, reader modes and visitors without JavaScript can all read. A prompt left in flow still needs a few rules drawn from the measurements: keep the input row last, scroll by `visualViewport.height` (never `scrollIntoView` or `innerHeight`) after appending output with the keyboard open, give the input 16 px text, and cancel `pointerdown` on any button that must not close the keyboard. The limits are plain: one simulated phone on iOS 26.5 with synthesised touches, the owner's fault was not visibly reproduced on the old terminal there, and nothing was measured on iOS 27, where the `interactive-widget` viewport key arrives only in the 27.3 beta with its `resizes-content` value reported broken.

**How to read the evidence.** Each claim links to its source and keeps the label its researcher gave it. "Primary" means a spec, vendor documentation, vendor source code, release notes or a vendor engineer's comment in a bug tracker; a library's own source is primary for what that library does, not for what Safari does. "Compat" means MDN browser-compat-data v8.1.9 (built 2026-11-12), parsed directly by a researcher: community-maintained and vendor-reviewed, near-primary for version numbers ([BCD](https://unpkg.com/@mdn/browser-compat-data/data.json)); another researcher labelled single files of the same data primary, and those labels are kept as given. "Community" means a blog, forum, third-party table, pull request or bug reporter. "Recalled" means the researcher stated it from memory without re-reading a source in this session; a link beside a recalled claim is the canonical page, added for the reader and not read unless the text says so, and where there is no link none was read. "Inference" marks reasoning by a researcher or by the measurer, not a sourced fact. Two kinds of first-hand measurement have no URL. Results **measured in the iOS 26.5 Simulator (iPhone 17e)** were taken on 2026-11-19 by the coordinating session (Xcode 27.2, runtime 23F77, a 390×844 pt screen at DPR 3, Safari with the software keyboard on, synthesised touches) on a probe page with the viewport tag `width=device-width, initial-scale=1, viewport-fit=cover`, and in one case on the site's old terminal itself; they sit in blockquote callouts, and the measurer's conclusions from them are marked as inference. Results from the previous day's report, `2026-11-18-mobile-web-game-controls.md`, were measured in the same runtime on a simulated iPhone 17 and are cited by that file name where this report relies on them. Three facts about the old terminal were also read from this repository's source for this report and are marked where they occur. Both kinds come from a Simulator and not from a phone: momentum, rubber-banding and two-finger gestures are not faithful, and a developer who tested Safari 26 on devices writes that "The simulator doesn't reproduce half of these issues" (community: [1ar.io](https://1ar.io/updates/safari-26-liquid-glass-web/)). Safari 27.0 shipped with iOS 27 on 2026-09-14 (the date as given in `2026-11-18-mobile-web-game-controls.md`); no iOS 27 runtime was available, so nothing here was measured on iOS 27. Screenshots of every probe state are listed in the probe note and kept in `minimal-terminal-shots/` in the session notes; they are not in the repository.

## The complaint is two faults, and the page owns only one

Each phrase of the complaint matches something measured or sourced, and the phrases do not share a cause.

| The owner's words | What the evidence shows | Can the page change it |
|---|---|---|
| "It's not anchored onto like right above the actual keyboard part" | About 100 pt of Safari's own chrome (address pill, form accessory bar) lay between the visible page and the keyboard in every layout measured. WebKit's source forces the accessory bar on for text inputs on an iPhone | No. The closest position is the bottom edge of the visible area, on top of Safari's bar |
| "the text bar just scrolls up so far that it blocks everything else from happening" | A frame fitted to `visualViewport` by script, which is the old terminal's method, was drawn at the top of the visible area and partly off it for an interval after focus. A locked `100dvh` shell was pushed 310 px up under the status bar. Both measured on the probe page | Yes, by not pinning or fitting the bar |
| "it just kind of floats all over the place" | A sticky bar came to rest with page text showing underneath it, then ended behind the keyboard after one short drag; the script-fitted frame jumped when its numbers caught up. Measured. Projects from 2024 to November 2026 report the same jumps | Yes, by the same change |
| "It's a recurring problem" | An iOS 26.0 system fault that shifted fixed elements, reported fixed in 26.1 and reported again through December 2025; a jump report on iOS 26.5 in June 2026; a keyboard-pinning fix merged on 2026-10-05 and then reverted | Only by not depending on the numbers that keep changing (inference) |

### Safari keeps about 100 pt of its own chrome between the page and the keyboard

> **Measured in the iOS 26.5 Simulator (iPhone 17e, 390×844 pt, DPR 3), Safari tab, software keyboard.** Values are CSS px unless marked pt.
>
> | Reading | Keyboard closed, toolbar expanded | Toolbar collapsed after scrolling | Keyboard open |
> |---|---|---|---|
> | `visualViewport.height` | 699 | 739 | **389**, constant in every run |
> | `visualViewport.offsetTop` | 0 | 0 | up to 310 (699 − 389) |
> | `window.innerHeight` | 699 | 739 | **389, 411, 487, 607 or 699** in the same keyboard-open state, depending on what last scrolled |
> | Bottom of the visible page, from the top of the screen | n/a | n/a | 435 pt |
> | Top edge of the keyboard, from the top of the screen | n/a | n/a | about 536 pt |
>
> The band between 435 and 536 pt holds Safari's floating address pill and the form accessory bar (previous, next and a tick). Both are translucent and the page keeps rendering behind them, but a page cannot put usable content there. The closest an input can get to the keyboard in a Safari tab is therefore the bottom edge of the visual viewport, directly above Safari's own bar. `window.scrollY` equals `visualViewport.pageTop`, and `getBoundingClientRect()` is relative to the visual viewport; sticky and fixed boxes hang off the layout viewport, which sits `offsetTop` above it. After the keyboard closed (by the tick, or by focus leaving the input) every reading returned to its starting value in every run. Needs confirming on a real iPhone and on iOS 27.

Nothing a page controls reaches into that band. WebKit's source shows why the accessory bar is always there: `requiresAccessoryView` returns yes on a small-screen device for text, password, search, email, URL, phone and number inputs, for `contenteditable` and for `<textarea>`. It returns no only while Writing Tools is presenting, when a host app sets `accessoryViewShouldNotShow` on its form input session, when a PDF is displayed, or when the focused element is of type none, colour or drawing or is one of the date and time pickers (primary: [WKContentViewInteraction.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/ios/WKContentViewInteraction.mm); [_WKFormInputSession.h](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/_WKFormInputSession.h)). The researcher infers that `inputmode`, `enterkeyhint`, `tabindex` and being the only input in a form do not remove it, and that `inputmode="none"` removes the keyboard along with it. One project states the same from the embedder's side: only a native app that embeds WebKit can turn the bar off (community: [srtdio #470](https://github.com/srtdio/app/pull/470)).

No Apple or WebKit statement was found on where the address pill sits while the keyboard is up, and no WebKit bug was found that treats the band as a defect. The nearest primary statement concerns the toolbar with the keyboard closed: Simon Fraser of WebKit wrote on 2025-10-01 that a `bottom: 0` fixed element sitting above the Liquid Glass controls is intended and that the colour filled in beneath it is a heuristic, and Wenson Hsieh added the next day that the fill is sampled from the page (primary: [WebKit bug 297779](https://bugs.webkit.org/show_bug.cgi?id=297779)). That the keyboard-open band is equally intended is the researcher's inference. An older bug is consistent with that reading: on the iOS 15 betas `visualViewport.height` ignored the address bar above the keyboard, and that was treated as a fault and fixed in 15.2 (community, read as a search summary: [WebKit bug 230225](https://bugs.webkit.org/show_bug.cgi?id=230225)). A developer testing Safari 26.x on real devices describes the strip from the page's side: the accessory bar shows a slice of the page that a fixed overlay's `backdrop-filter`, `z-index` and opacity do not reach, and Safari tints its toolbar from fixed or sticky elements within about 3 px of the bottom edge, even at `opacity: 0` (community, 2026-05-13: [1ar.io](https://1ar.io/updates/safari-26-liquid-glass-web/)). That agrees with the measurement that the page keeps rendering behind the bars.

Two community reports bear on the band. One chat project logged an empty gap of about 40 px between its composer and the keyboard and blamed a stale bottom safe-area inset while Safari pans (community: [hype-armor #61](https://github.com/hype-armor/chat/issues/61)); the notes do not say whether that was a Safari tab. Another sized its shell from `visualViewport`, merged the change on 2026-10-05 untested on a device, and reverted it so that Safari's AutoFill bar no longer covered the composer (community: [srtdio #470](https://github.com/srtdio/app/pull/470)). The researcher reads the revert as direct evidence that anything placed lower than the visual viewport's bottom ends up under Safari's strip (inference). Whether the band shrinks to the accessory bar alone in Safari's Top tab layout, or in a Home Screen web app where there is no bottom pill, is also inference; neither was measured.

### Every pinned bar was misplaced at some point; the prompt left in flow never was

The probe page is 60 lines of monospace text followed by a composer: a row holding a real `<input>` (16 px text, 44 px tall) with a row of buttons under it. A 32 px title bar is `position: sticky; top: 0`. A query parameter chooses how the composer is placed.

> **Measured in the iOS 26.5 Simulator (iPhone 17e).** Rectangles are top…bottom in CSS px from the top of the visible area (the visual viewport), which was 389 px tall with the keyboard open.

Composer at 281…389, its bottom edge exactly on the bottom of the visible area; input row at 287…331. Unchanged at 0.6 s, 1.5 s and 3 s. Nothing overlapped anything | On a page shorter than the screen (20 lines) the input was centred instead, at 172…216, with blank page under the composer and the input still directly under the last line of output |
> | `flow` with the buttons moved above the input, so the input row is the very last thing in the document | Input at 345…389: flush with the bottom of the visible area, directly on Safari's pill and accessory bar. No script. Unchanged at 0.6 s, 1.5 s and 3 s | The closest to the keyboard that any run put an input |
> | `sticky`: the document scrolls; the composer is `position: sticky; bottom: 0` | `window.scrollY` jumped from 330 to 795. Typing would bring it back; scrolling loses it again |

The measurer's own reading of these results is inference, not measurement, and it is this: anything pinned to the bottom, by CSS or by script, is positioned from numbers that are wrong or late while the keyboard moves, and at best ends 100 pt above the keyboard; nothing pinned can be right on the keyboard; and the only layout that needed no script and never misplaced the input is the input as the last element of a normally scrolling document, where Safari places it and the page only has to keep it last. **Where the measurement and the notes disagree.** Two researchers, reasoning from web sources with no keyboard-open data, rated a sticky bottom row highly. One called `position: sticky; bottom: 0` on the last child of the log the best fit for a scrolling document; the other called a fixed or sticky composer over a scrolling log as robust as an in-flow input, though less like a terminal (both inference). The probe measured the opposite once the keyboard opened. Neither side is conclusive: the inferences were never tested, and the measurement is one simulated phone with synthesised touches. Both agree that the sticky row is sound while the keyboard is closed. The earlier report recommended, also as inference, sizing a fixed layer from `visualViewport` events for the game (`2026-11-18-mobile-web-game-controls.md`); that layer has no text input, and the keyboard is what breaks the technique here.

**How thin the support for the favoured layout is.** The in-flow prompt rests on one Simulator session and a reading of WebKit's source. The researchers found no outside write-up of the pattern, no primary WebKit statement that an in-flow input is reliably revealed, and no verified terminal-style portfolio built around a visible input in flow. The source does explain the measurement. On focus, WebKit's UI process works out the visible area above the keyboard's frame, allowing for the browser's own obscured insets, and scrolls the page's scroll view to centre the focus or selection rectangle in that area; the constants are 106 pt for the least height it will use above the keyboard, 50 pt for the distance from the keyboard that triggers a scroll, and an 8 pt caret offset from the window edge (primary: [WKWebViewIOS.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/ios/WKWebViewIOS.mm)). When an accessory bar is required, which is always for a text input on an iPhone, the scroll is forced (primary: [WKContentViewInteraction.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/ios/WKContentViewInteraction.mm)). The measurer's reading matches: Safari tries to centre the input, and on a long page the scroll range runs out first, which leaves the document's last element on the bottom edge. On the 20-line page the input sat at 172…216 of 389 px, which is the centre. It follows, as inference, that the prompt reaches the bottom edge only while little or nothing follows it in the document and enough content precedes it.

### A pinned bar is placed from numbers that are late or wrong

On iOS the on-screen keyboard resizes only the visual viewport. The layout viewport, the viewport units and `position: fixed` all ignore it, so fixed elements stay where they were and the keyboard can cover them; Chrome on Android has behaved the same way by default since Chrome 108 in November 2022 (primary: [Chrome for Developers](https://developer.chrome.com/blog/viewport-resize-behavior); [WebKit standards-positions #65](https://github.com/WebKit/standards-positions/issues/65)). `svh`, `lvh` and `dvh` follow only the toolbar (recalled), a community guide makes the point that `dvh` is no keyboard fix (community: [DEV, deanliu](https://dev.to/deanliu/dvh-is-not-a-keyboard-fix-picking-the-right-viewport-tool-on-mobile-446o)), and the probe's `100dvh` shell did not change height. The researcher concludes (inference) that no CSS unit can size a layout to the space above the keyboard on shipping iOS, and that `window.visualViewport` is the only signal a script has.

That signal is one trustworthy number among untrustworthy ones. `visualViewport.height` read 389 in every keyboard-open run, while `window.innerHeight` took five values in the same state. This is a disagreement with the primary account above, under which the keyboard leaves everything but the visual viewport alone. One researcher's explanation (inference) is that WebKit reports the unobscured layout size, which varies with the state of Safari's own chrome as well as with the keyboard. A community fix tested in the iOS 26.5 Simulator sides with the measurement: it says iOS 26 shrinks `innerHeight` to the visible height once it pans the page, so keyboard detection that compares the two fails; it switched to `documentElement.clientHeight`, which the probe did not log (community: [cc-haha #1757](https://github.com/NanmiCoder/cc-haha/pull/1757)). The formula most guides give for a pinned bar, `bottom = innerHeight − visualViewport.height − visualViewport.offsetTop`, depends on that number (community: [DEV, deanliu](https://dev.to/deanliu/dvh-is-not-a-keyboard-fix-picking-the-right-viewport-tool-on-mobile-446o)); the researcher infers it is unstable and that a script should position against `visualViewport` alone.

Timing is the second problem. In the `shellvv` probe the page had already scrolled 310 px while `visualViewport` still reported an offset of 0, and for that interval the script drew the bar at the top of the visible area. Samples were 0.6 s apart, so the interval is shorter than that and otherwise unmeasured. Web sources describe the same lateness from other angles: the keyboard inset changes all through the keyboard animation (community: [DEV, deanliu](https://dev.to/deanliu/dvh-is-not-a-keyboard-fix-picking-the-right-viewport-tool-on-mobile-446o)); iOS applies a further pan after the animation ends, 337 px in one project's log (community: [cc-haha #1757](https://github.com/NanmiCoder/cc-haha/pull/1757)); and older WebKit bugs, read only as search summaries, record the visual viewport resizing only at the end of the keyboard animation when the browser UI is expanded, and on iOS 12 no `resize` event at all when the keyboard opened (community: [WebKit bug 176205](https://bugs.webkit.org/show_bug.cgi?id=176205), [WebKit bug 198347](https://bugs.webkit.org/show_bug.cgi?id=198347)). When a user reported in June 2026 that a Vercel-built Ask AI box jumped up at random on focus in Safari on iOS 26.5, while Chrome on the same phone and landscape were steady, the Vercel responder diagnosed a race between the visual viewport and the keyboard resize rather than a CSS breakpoint problem (primary for Vercel's diagnosis of its own interface: [Vercel community](https://community.vercel.com/t/ask-ai-ui-is-broken-on-mobile-layout/44380)). No WebKit source was found that states the order of events.

Locking the page does not stop Safari moving it. The `shell` probe scrolled 310 px with `overflow: hidden` on `html` and `body`. WebKit's Simon Fraser is quoted as saying that scrolling is allowed whenever the visual viewport is smaller than the layout viewport, which is exactly the keyboard-open state (primary, quoted secondhand in [interop #84](https://github.com/web-platform-tests/interop/issues/84)). A shell layout therefore has to chase the pan as well as the resize, and the fixes written between September and November 2026 do: they lock `html` and `body`, size a fixed root from `visualViewport.height` and `offsetTop`, and undo the late pan (community: [srtdio #470](https://github.com/srtdio/app/pull/470), [cc-haha #1757](https://github.com/NanmiCoder/cc-haha/pull/1757), [herdsman #443](https://github.com/jirathip-dev/herdsman/issues/443)).

The record explains why the owner sees the fault recur. iOS 26.0 shipped a fault that moved fixed elements as the scroll direction changed and left `visualViewport.offsetTop` stuck at 24 after the keyboard closed, with a lasting 24 px gap between `innerHeight` and `visualViewport.height`, cured only by relaunching Safari (community reports on [WebKit bug 297779](https://bugs.webkit.org/show_bug.cgi?id=297779), filed 2025-08-22; [Apple forums 800125](https://developer.apple.com/forums/thread/800125)). Wenson Hsieh of WebKit said on 2025-09-16 that the fault lay in a system component and that the fix covers Safari and every app embedding WebKit (primary: [WebKit bug 297779](https://bugs.webkit.org/show_bug.cgi?id=297779)). Reporters found it fixed in the 26.1 beta and release, not in 26.0.1. Then came reports of it on iOS and iPadOS 26.1 (2025-11-07), of sticky footer and textarea trouble on 26.1 that improved and came back in December 2025 with a suspicion that the keyboard app matters, and of a Chrome-only sticky shift on iOS 26.6.1 (2026-10-01) (community: same bug). The bug is closed as moved, with no fix version recorded. In the Simulator on 26.5 the stuck offset did not reproduce. Reports name other triggers a Simulator session does not cover: bottom-anchored elements jumping halfway up the screen on scroll when Reduce Motion and Prefer Cross-Fade Transitions are on (community, iOS 26.0: [Apple forums 800125](https://developer.apple.com/forums/thread/800125)); a fixed header shifted down by about the keyboard's height after a swipe-back in an embedded web view while the keyboard is up (community: [Apple forums 797097](https://developer.apple.com/forums/thread/797097)); and in Home Screen web apps, which have older keyboard bugs of their own, a bar left about 59 px too high until the app is force-quit and a fixed bar drifting by 1 to 21 px with the viewport offset at zero (community: [cederhook](https://dev.to/cederhook/fixing-the-ios-standalone-pwa-keyboard-bug-that-shrinks-your-viewport-for-good-63d), [plushie #228](https://github.com/donecast/plushie/pull/228)).

### iOS 27 has not changed this yet, and its new viewport key does not promise to

This subsection is sources only, because no iOS 27 runtime was available. WebKit's feature post for Safari 27.0 lists no fix to `visualViewport`, keyboard geometry, safe areas or the accessory bar in the part the researchers read, which was the first 100,000 or so of about 147,000 characters. The nearest items are a fix for the page scrolling by itself while a text selection is adjusted inside a fixed element, and one for viewport units after the viewport is resized (primary: [WebKit, Safari 27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/)). Whether the iOS 26 faults persist on 27.0 to 27.2 is unknown; nothing on bug 297779 after October 2026 mentions Safari 27.

The `interactive-widget` viewport key lets a page ask for the layout viewport to resize with the keyboard (`resizes-content`), for only the visual viewport to resize (`resizes-visual`, the default) or for neither (`overlays-content`) (primary: [MDN, viewport meta](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport)). WebKit has implemented it: the tracking bug filed in 2023 is resolved as fixed, and the feature flag landed on 2026-08-13 (primary: [WebKit bug 259770](https://bugs.webkit.org/show_bug.cgi?id=259770), [WebKit bug 321543](https://bugs.webkit.org/show_bug.cgi?id=321543)). It is not in a public release. On 2026-11-06 a WebKit engineer, Tim Nguyen, answered a reporter who found the key ignored on iOS 27.2 by saying the implementation is in the iOS 27.3 beta and not in 27.2; testers on that beta report that `resizes-visual` and `overlays-content` work, and that with `resizes-content` the page gives a small bump and the input stays hidden behind the keyboard (primary for the engineer, community for the testers: [WebKit bug 259770](https://bugs.webkit.org/show_bug.cgi?id=259770)). WebKit has published no standards position on the key (primary: [WebKit standards-positions #65](https://github.com/WebKit/standards-positions/issues/65)), and its tests include one named for an iOS quirk that ignores the key, which the researcher takes to mean that some sites are quirk-listed (primary, found by code search: [WebKit source](https://github.com/WebKit/WebKit)). A third-party release tracker quotes a Safari note adding the key with all three values; neither researcher could open Apple's own notes to confirm it, and they read the tracker differently, one as a 27.3 beta note and one as conflicting with the bug thread (community: [Releasebot](https://releasebot.io/updates/apple/safari)). The VirtualKeyboard API and `env(keyboard-inset-*)` are Chromium-only (recalled).

Two inferences bound what the key could do for this page. Even a working `resizes-content` most likely resizes the layout to the visual viewport, which ends above Safari's pill and accessory bar and not at the keyboard; that is unconfirmed on any device. And because the key already works in Chrome on Android (108 and later) and in Firefox for Android (from 132 or 133, depending on the source), it can only be an enhancement whose absence must not break the layout (primary: [Chrome for Developers](https://developer.chrome.com/blog/viewport-resize-behavior); community: [bram.us](https://www.bram.us/2026/09/11/webkit-supports-interactive-widget-and-hopefully-safari-will-too/), [HTMHell](https://htmhell.dev/adventcalendar/2024/4/)). A page with nothing pinned does not depend on it either way.

### The Simulator did not reproduce the fault on the old terminal itself

> **Measured in the iOS 26.5 Simulator (iPhone 17e): the site's old terminal as it is on this branch, opened from the header on `/`.** It opens full screen with the keyboard up. The prompt row sits at the bottom of the script-fitted frame, about 100 pt above the keyboard, with Safari's pill and accessory bar in the gap. iOS showed a "Passwords" strip on the keyboard and started the line in capitals. So the fault as the owner describes it was not reproduced. What the probe did produce are two states that fit the description: the interval of stale readings in the `shellvv` case, when the bar is drawn at the top of the visible area, and the bar left behind the keyboard after a drag, which was measured in the `sticky` case and not on a script-fitted frame. The measurer proposes these as the mechanisms behind the complaint; that is inference until it is seen on the owner's phone.

The old terminal's source states the assumptions it was built on (read from the repository for this report: `src/components/terminal/useTermWindow.ts` and the phone rules in `src/app/globals.css`). Its comments say that fitting the frame to the visual viewport puts the input row on the keyboard, and that writing the geometry straight from the viewport's own events keeps the frame where the viewport is in the same frame it moved. The hook also treats the keyboard as open when `window.innerHeight` exceeds `visualViewport.height` by more than 120. Each assumption meets a measurement above: the visual viewport ends about 100 pt short of the keyboard; the first readings after focus were stale; and with the keyboard open the probe's `innerHeight` values put that difference at 0, 22, 98, 218 or 310. The old terminal's own `innerHeight` was not logged, and the flag only switches the input row's bottom padding by the bottom safe-area inset, which the earlier report measured as 0 in portrait Safari (`2026-11-18-mobile-web-game-controls.md`), so the flag alone does not explain the complaint. Pairing the source with the probe's numbers is this report's inference.

## Keep the prompt last, scroll by the visual viewport, type at 16 px

The in-flow layout is not free of rules. The first is already in the callout above: whatever follows the input in the document sits between it and Safari's bar. With a row of buttons under it the input row rested at 287…331; as the last row it rested at 345…389. The probe also exercised what a live prompt does, and several of those actions have a wrong way that looks reasonable. ### After appending output, `scrollIntoView` was 98 px out and the visual viewport was right

A terminal appends output above the prompt while the keyboard is open, which pushes the prompt out of the visible area, and the page then has to bring it back. The obvious call failed, and the measurer concludes (inference) that a page appending output with the keyboard open must scroll by `visualViewport.height`, never by `scrollIntoView` and never by `innerHeight`. This contradicts one researcher's untested suggestion to call `input.scrollIntoView({ block: "end" })` after each command (inference), and it leaves the other researcher's rule for a scrolling document, `window.scrollTo(0, document.documentElement.scrollHeight)`, unmeasured with the keyboard open; that researcher found no primary data on either call in that state. The one outside report is from jQuery Terminal, where a user who called `scrollIntoView()` on the prompt line from a `visualViewport` resize listener kept the prompt visible but got jumps while typing (community: [jquery.terminal #914](https://www.github.com/jcubic/jquery.terminal/issues/914)). If the page re-checks the prompt's position at all, the researchers advise (inference) doing so on `visualViewport` `resize` and `scroll` and on `focusout`, once per animation frame, so that a late event or a stuck offset does not leave it wrong.

The keyboard also sets how much output can be seen. With it open the visible page is 389 px of the 699 px available with it closed, less the prompt row. Two conventions exist for what happens after a command. The probe's form kept focus and the keyboard after Return. The Vercel chatbot does the opposite on phones: after a send it re-focuses its textarea only when the window is wider than 768 px, which by the researcher's reading lets the keyboard close and gives the reply the whole screen (primary, the project's source: [multimodal-input.tsx](https://github.com/vercel/chatbot/blob/main/components/chat/multimodal-input.tsx)). The evidence says both are available; which suits a terminal session is a design choice.

### Only a tap raises the keyboard, and an ordinary button lowers it

iOS shows the keyboard on focus only while the user is interacting: a focus made synchronously inside a tap or click handler, a move of focus while the keyboard is already up, or a hardware keyboard. WebKit's focus-policy code says so (primary: [WKContentViewInteraction.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/ios/WKContentViewInteraction.mm)). A WebKit engineer explained in 2019 that programmatic focus without a gesture is kept from raising the software keyboard because of the screen space, scrolling and zooming it costs (primary: [WebKit bug 195884](https://bugs.webkit.org/show_bug.cgi?id=195884)), and MDN's compatibility data notes that `focus()` on an input has no effect until the user has interacted with the page when no hardware keyboard is attached (primary: [BCD, HTMLElement](https://github.com/mdn/browser-compat-data/blob/main/api/HTMLElement.json)). A focus deferred into a promise or a `setTimeout` after a tap does not raise it either (community: [Elixir Forum](https://elixirforum.com/t/triggering-focus-on-mobile-via-js-module/67915)). The probe's one test of this agrees: `input.focus()` inside another button's click handler opened the keyboard. It did not record where the input landed after that script focus.

`focus({ preventScroll: true })` has been supported since Safari on iOS 15.5 (primary: [BCD, HTMLElement](https://github.com/mdn/browser-compat-data/blob/main/api/HTMLElement.json)), and WebKit's reveal returns early when that option is set (primary: [WKContentViewInteraction.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/ios/WKContentViewInteraction.mm), [WebPageIOS.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/WebProcess/WebPage/ios/WebPageIOS.mm)). The researcher infers that a script focus with `preventScroll` suppresses Safari's own reveal. For an in-flow prompt that reveal is the whole mechanism, so the option would switch it off (inference, not verified on a device). Another researcher found no sign in the code that `scroll-margin` or `scroll-padding` feed the reveal, and treats them as not honoured for it (inference, unverified).

The two button results give each control near the prompt a choice made by one call. A button that cancels `pointerdown` keeps the keyboard, which suits history and completion keys; a button that does not cancel it dismisses the keyboard, which suits a command chip whose output should get the whole screen. The pairings are inference; the two behaviours are measured.

### A 16 px input never zooms; a 13 px one zoomed to 1.231

WebKit's source computes the focus zoom as 16 divided by the field's computed font size, clamped to the page's minimum and maximum scale, and skips it when the change would be under 10% (primary: [WKWebViewIOS.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/ios/WKWebViewIOS.mm)). The probe matched the formula at both sizes it tried. By the same arithmetic a 15 px field would not zoom (1.067) and a 14 px field would (1.143). That is inference from the source; one forum post puts the threshold at 15 px or less (community: [WeWeb forum](https://community.weweb.io/t/iphone-autofocus-issue/21223.md)), and most guides say anything under 16 px zooms (community: [CSS-Tricks](https://css-tricks.com/?p=339455), [takazudo](https://takazudo-zudo-tauri.pages.dev/pj/zudo-tauri/docs/mobile/ios-input-auto-zoom)). Neither 14 nor 15 px was measured, and 16 px is safe under every reading. Mobile Safari does not zoom back out on blur (community: [commit note](https://graphql-demo.kriasoft.com/discoman/python-tdd/commit/79706e817aae843db28b6a4b0ef7c3cdc76dfa8b?files=src)).

`maximum-scale=1` also stops the zoom where it is honoured, because the maximum scale is the clamp (primary: same source). MDN warns against limiting zoom and notes that iOS 10 and later ignore the limit for the user's own pinch (primary: [MDN, viewport meta](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport)), which matches the earlier report's finding that `user-scalable=no` and `maximum-scale=1` have been ignored in iPhone Safari since iOS 10 and are obeyed by Chrome on Android unless the user forces zoom on (`2026-11-18-mobile-web-game-controls.md`). The researcher recalls that on Android the tag therefore blocks pinch zoom, a WCAG 1.4.4 failure, and infers that a 16 px input with the viewport tag left alone avoids the focus zoom at no accessibility cost.

### A form and four attributes make a command line

The probe's input sat in a `<form autocomplete="off">` and carried `enterkeyhint="send"`, `autocapitalize="none"`, `autocorrect="off"` and `spellcheck="false"`. Return submitted the form, and iOS showed neither the "Passwords" strip nor a capital first letter, both of which the old terminal showed. Which attribute removed the strip was not isolated, and one project claims Safari ignores `autocomplete="off"` in its AutoFill heuristics (community: [srtdio #470](https://github.com/srtdio/app/pull/470)). The old terminal's prompt already had `autocomplete="off"` and `spellcheck="false"`, had neither `autocapitalize` nor `autocorrect`, and was not inside a form (read from the repository for this report: `src/components/terminal/ShellView.tsx`). That fits both the capitals and the project's claim, as inference.

`autocapitalize` has been supported since Safari on iOS 10.3 (primary: [BCD, HTMLElement](https://github.com/mdn/browser-compat-data/blob/main/api/HTMLElement.json)); `enterkeyhint` and `inputmode` appear in the same data only as mirroring desktop Safari, and the researcher recalls both as long supported on iOS. The researcher recommends, as inference, a `submit` handler as the command signal and not `keydown`: Android's virtual keyboards do not report usable key values during composition, while `beforeinput` and `input` are dependable on both platforms (recalled). With one input in the form, the accessory bar's previous and next arrows are disabled (recalled).

### New output is pinned by script, and only for a reader already at the bottom

Scroll anchoring shipped in Safari 27 and is on by default; `overflow-anchor: none` opts out (primary: [WebKit, Safari 27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/), [WebKit, WWDC26](https://webkit.org/blog/17967/news-from-wwdc26-webkit-in-safari-27-beta/); compat: [BCD](https://unpkg.com/@mdn/browser-compat-data/data.json) lists `overflow-anchor` from Safari and iOS Safari 27). It was absent before, and a third-party table and one library's README still say Safari lacks it (community: [web-features explorer](https://web-platform-dx.github.io/web-features-explorer/features/overflow-anchor), [use-stick-to-bottom](https://github.com/stackblitz-labs/use-stick-to-bottom)). It does not pin a log. The algorithm holds an anchor node still against layout changes above it, and a transcript grows below (spec: [CSS Scroll Anchoring](https://drafts.csswg.org/css-scroll-anchoring/)). On every iOS version, then, the page pins new output itself.

The shipped pattern is the same everywhere: note whether the reader was at the bottom before the append, and scroll only if so. The Vercel chatbot counts within 100 px of the end as the bottom, marks the user as scrolling for 150 ms after each scroll event through a passive listener, and on a mutation or resize jumps instantly to the end inside `requestAnimationFrame`, only when the reader is at the bottom and not scrolling; otherwise it shows a button that scrolls to the bottom (primary, the project's source: [use-scroll-to-bottom.tsx](https://github.com/vercel/chatbot/blob/main/hooks/use-scroll-to-bottom.tsx), [messages.tsx](https://github.com/vercel/chatbot/blob/main/components/chat/messages.tsx)). use-stick-to-bottom does the same with a `ResizeObserver` and lets the user cancel stickiness by scrolling up (primary, README: [use-stick-to-bottom](https://github.com/stackblitz-labs/use-stick-to-bottom)), and react-virtuoso's `followOutput` follows only when the list is already at the bottom (primary, docs: [Virtuoso API](https://virtuoso.dev/react-virtuoso/api-reference/virtuoso/)). The researcher's own suggestion is a tighter test, a tolerance of 2 to 4 px or an `IntersectionObserver` on a sentinel after the last line (inference; the observer has been in iOS since 12.2, compat: [BCD](https://unpkg.com/@mdn/browser-compat-data/data.json)).

Three iOS details bear on the pin. Before Safari 27 a `scrollTo` during a momentum scroll interrupted the fling (primary, listed as fixed: [WebKit, WWDC26](https://webkit.org/blog/17967/news-from-wwdc26-webkit-in-safari-27-beta/)), so on iOS 26 the researcher advises holding the pin back while a touch or momentum is in progress (inference). The `scrollend` event exists from Safari 26.2 (compat: [BCD](https://unpkg.com/@mdn/browser-compat-data/data.json)) but is not fired on `VisualViewport` (primary: [WebKit bug 304147](https://bugs.webkit.org/show_bug.cgi?id=304147)). And `scroll-behavior: smooth`, in iOS since 15.4 (compat: [BCD](https://unpkg.com/@mdn/browser-compat-data/data.json)), animates every programmatic scroll: Headless UI forces it to `auto` while it restores scroll positions because the smooth version ends in the wrong place (primary, the library's source: [handle-ios-locking.ts](https://github.com/tailwindlabs/headlessui/blob/main/packages/%40headlessui-react/src/hooks/document-overflow/handle-ios-locking.ts)). The researcher's recommendations are all inference: an instant jump per append; smooth scrolling only behind `prefers-reduced-motion: no-preference`; no `flex-direction: column-reverse`, which reports a negative `scrollTop` (community: [VueUse issue](https://github-redirect.dependabot.com/vueuse/vueuse/issues/2576), [Ionic forum](https://forum.ionicframework.com/t/scroll-position-ios-doesnt-set/188123)) and inverts reading and find order; no scroll-snap; and `overflow-anchor: none` on sentinel elements. With the keyboard open, the measured rule in the previous section overrides the generic one.

### Overscroll containment and scroll locks stop where iOS says so

`overscroll-behavior` has been in Safari since 16.0, but only on boxes that actually overflow: `contain` on a short log does nothing until the log is longer than its box (compat: [BCD](https://unpkg.com/@mdn/browser-compat-data/data.json), marked partial with that note). Chrome dropped the limit in 144, stable on 2026-01-13, and Firefox in 150; WebKit's bug is still new and unassigned, last modified 2026-11-04, with Simon Fraser explaining in 2024 that non-scrollable boxes would have to be represented in the scrolling tree (primary: [Chrome 144 beta](https://developer.chrome.com/blog/chrome-144-beta), [WebKit bug 243452](https://bugs.webkit.org/show_bug.cgi?id=243452)). Headless UI's source records the same limit and works around it by looking for an ancestor that really overflows (primary, the library's source: [handle-ios-locking.ts](https://github.com/tailwindlabs/headlessui/blob/main/packages/%40headlessui-react/src/hooks/document-overflow/handle-ios-locking.ts)). On a document that scrolls, the root is the only box that matters. `overscroll-behavior: none` on `html` stops the document's rubber band on iOS 16 and later when the document is scrollable (recalled), but the earlier report lists community accounts of it being ignored (`2026-11-18-mobile-web-game-controls.md`), and no primary source covers `html` against `body` on iOS 26 or 27.

No CSS-only scroll lock is reliable on iOS Safari. `overflow: hidden` on the body holds in the simple case, but WebKit lets the page scroll by design when the browser UI is collapsed and whenever the visual viewport is smaller than the layout viewport, the state the `shell` probe hit (primary, quoted secondhand: [interop #84](https://github.com/web-platform-tests/interop/issues/84); the two WebKit bugs it cites were open in 2022 and were not re-checked). Current libraries therefore combine `overflow: hidden` with a non-passive `touchmove` handler that calls `preventDefault()` outside scrollable descendants. Headless UI does this and restores `scrollY` on unlock, without putting `position: fixed` on the body (primary, the library's source: [handle-ios-locking.ts](https://github.com/tailwindlabs/headlessui/blob/main/packages/%40headlessui-react/src/hooks/document-overflow/handle-ios-locking.ts)). react-remove-scroll does it and blocks pinch zoom by default (community: [README](https://github.com/theKashey/react-remove-scroll)). body-scroll-lock was last pushed on 2023-03-30 and had 119 open issues on 2026-11-19 (community: [README](https://github.com/willmcpo/body-scroll-lock), [GitHub API](https://api.github.com/repos/willmcpo/body-scroll-lock)). `showModal()` does not lock the page behind a dialog (recalled). Non-passive touch handlers carry a cost of their own on iOS 26 and earlier: Safari 27 lists as fixed a fault in which a page's touch handling blocked the text-selection handles (primary: [WebKit, WWDC26](https://webkit.org/blog/17967/news-from-wwdc26-webkit-in-safari-27-beta/)).

The researcher's inference is that a terminal page needs a lock only when it puts an overlay over a scrolling document. The old terminal was such an overlay, a full-screen dialog. A page that is itself the document has nothing to lock.

### Sticky bars hang off the layout viewport; wide output must wrap

The probe's title bar, `position: sticky; top: 0`, read `top: -310` with the keyboard up, because sticky and fixed boxes hang off the layout viewport, which then sits 310 px above the visible area. A sticky header is therefore off screen while the visitor types (measured in the iOS 26.5 Simulator, iPhone 17e). Otherwise sticky positioning is old and mostly sound on iOS, unprefixed since 13 (compat: [BCD](https://unpkg.com/@mdn/browser-compat-data/data.json)), with two recent footnotes. Safari 26 tints its toolbar from fixed or sticky elements near the viewport edge (primary: [WebKit bug 297779](https://bugs.webkit.org/show_bug.cgi?id=297779); community: [jahir.dev](https://jahir.dev/blog/safari-toolbar)). Safari 27 lists as fixed sticky elements flickering after a scroll and a regression that drew sticky elements inside overflow containers in front of content meant to overlap them (primary: [WebKit, WWDC26](https://webkit.org/blog/17967/news-from-wwdc26-webkit-in-safari-27-beta/)).

Safe areas matter less than the viewport tag suggests. The earlier report measured `env(safe-area-inset-*)` as 0 on every side in portrait Safari and 62 px at each side in landscape (`2026-11-18-mobile-web-game-controls.md`), so in a portrait tab bottom padding from the inset adds nothing, and in landscape full-width text needs side padding. `viewport-fit` itself is described as broken since Safari 26 (community: [bram.us](https://www.bram.us/2026/09/11/webkit-supports-interactive-widget-and-hopefully-safari-will-too/)), and a WebKit regression report on `viewport-fit=cover`, bug 301108, was still new when the notes were written (primary: split from [WebKit bug 300965](https://bugs.webkit.org/show_bug.cgi?id=300965)).

For wide output, iOS decides between a nested horizontal scroller and the vertical page by the gesture's first direction, so a `pre` with its own `overflow-x: auto` mostly works (recalled). The real risk is the page itself overflowing sideways, from a long URL or hash or a `pre` with no scroller of its own, after which Safari lets the whole page pan or zooms it out (recalled). The tools are `overflow-wrap: anywhere` (Safari and iOS 15.4) and `overflow: clip` (16), which unlike `hidden` creates no scroll container and so does not break sticky positioning (compat: [BCD](https://unpkg.com/@mdn/browser-compat-data/data.json); spec: [CSS Overflow 3](https://drafts.csswg.org/css-overflow-3/)). The researcher's recommendations are inference: `white-space: pre-wrap` with `overflow-wrap: anywhere` for ordinary output; sideways scrolling kept for ASCII art and tables, each in its own `overflow-x: auto; overscroll-behavior-x: contain` box; `overflow-x: clip` on the page wrapper; and no `touch-action: pan-y` on the log, because it forbids sideways panning of nested blocks and pinch zoom.

On selection the researchers differ in a small way. One advises against `user-select: none` anywhere in the log on iOS 26 and earlier, where Safari 27's notes show it caused selection jumps and wrong Find in Page positions (primary: [WebKit, WWDC26](https://webkit.org/blog/17967/news-from-wwdc26-webkit-in-safari-27-beta/)), and would draw prompt glyphs as `::before` pseudo-elements. The other would put `user-select: none` on the glyph's own `<span>` and notes that reader modes drop CSS-generated text (community: [Sara Soueidan](https://sarasoueidan.com/blog/tips-for-reader-modes/)). Both are inference; for a glyph that is decoration, being dropped is harmless.

### xterm.js treats mobile as outside its scope

In the open issue on touch support, filed 2025-07-20, one maintainer describes mobile support as essentially absent beyond what browsers map automatically and the frontend as built around a standard keyboard and a mouse; the other said on 2025-07-24 that touch support would need the DOM renderer or screen-reader mode, and that mobile input is outside the library's scope and not a priority for him (primary: [xterm.js #5377](https://github.com/xtermjs/xterm.js/issues/5377)). A touch-scrolling fix was committed on 2026-02-08, and the issue was dropped from the 7.0.0 milestone a month later and remains open. One user in the thread said mobile scrolling seemed worse in 6.0.0, whose release notes record a reworked viewport and scroll bar, and another swapped the helper input for a password field to get round Gboard (community, same thread; primary for the release notes: [releases](https://github.com/xtermjs/xterm.js/releases)). An unmerged pull request from January 2026 traces dropped Chinese punctuation and doubled emoji on iOS Safari to the way input events arrive outside the composition flow; the maintainer replied that he has no iOS device (primary: [PR #5614](https://github.com/xtermjs/xterm.js/pull/5614)). The older umbrella issue, opened in 2017 and closed in 2021, shows the same class of fault for years: predictive text interfering, a keyboard that replaces the whole line on delete (primary, the project's tracker: [xterm.js #1101](https://github.com/xtermjs/xterm.js/issues/1101)).

The researcher's reading is that these follow from the architecture (inference). The system keyboard, autocorrect and input methods edit a textarea the user cannot see, and the library turns the difference into keystrokes, so composition timing and line-replacing keyboards produce duplicates and drops. The library owns scrolling, so native momentum and tap-to-top are lost. Rows drawn on a canvas or by WebGL are not selectable text. A read-only portfolio shell with about ten commands needs none of what that architecture buys, which is terminal escape parsing, cursor addressing and an alternate screen.

### DOM terminals and chat apps all chase `visualViewport`

jQuery Terminal is the one terminal library that documents an approach to phones, and it is the closest relative of the site's old terminal. Its author states the problem as the measurements do: on iOS the keyboard does not change layout sizes in CSS, so the keyboard opens over the bottom of a full-height page. His fix writes the height from a `visualViewport` resize listener into a CSS variable with a `100dvh` fallback. He reported that it does not work fully: the cursor line was hidden after a blur and refocus, and focus sometimes failed (primary: [jquery.terminal #914](https://www.github.com/jcubic/jquery.terminal/issues/914)). The project's wiki adds that the terminal has to start disabled on phones so that a finger tap can activate it, which fits WebKit's rule that only a tap raises the keyboard (primary: [wiki](https://github.com/jcubic/jquery.terminal/wiki/Mobile-Web-Terminal-and-Responsive-Text)). The researcher's inference is that even a DOM-text terminal with native scrolling fights iOS as soon as it pins the prompt to the bottom of a full-height fixed box.

Chat interfaces are the nearest solved analogue, and they are only mostly solved. The Vercel chatbot's layout is the pattern the `shell` probe reproduced in miniature (inference; the chatbot itself was not loaded in the Simulator), and the June 2026 jump report above concerns another Vercel-built interface. The smaller projects of September to November 2026 converge on one technique: lock `html` and `body`, size the shell from `visualViewport`, keep only the thread scrolling, and undo iOS's late pan. One telemetry-driven author abandoned the viewport explanation altogether after logging drift with the viewport offset at zero (community: [plushie #228](https://github.com/donecast/plushie/pull/228)), and an issue title in another project describes the chat jumping away from the input line when the keyboard opens (community, not read in full: [hermes-agent #110414](https://github.com/NousResearch/hermes-agent/issues/110414)). The trackers of the larger chat and component libraries were not reached, and no engineering write-up from Slack, Discord, Telegram, Stream or Intercom was found.

The balance of the record is lopsided, and the researcher sorts it into two layers (inference). Input-corruption faults (duplicates, dropped punctuation, fights with autocorrect) come from a hidden input whose value is turned into keystrokes; a visible input whose value is read on submit avoids them. Keyboard-covers-prompt faults come from pinning the prompt to the bottom of a fixed-height box; an input in flow hands that job to Safari. No head-to-head comparison or user study was found. The researcher's ranking for this site puts a real visible `<input>` in flow first, a fixed or sticky composer second, a hidden input with a drawn caret third and `contenteditable` last; the measurements above bear on the second place.

### What carries over: tap-to-run chips, a way back to the latest line, 44 pt targets

Chat interfaces share two conventions that the researcher says transfer directly (inference): scroll to new output only while the reader is near the bottom and offer a control to return there otherwise, and do not hold the keyboard open after a send on a phone. A third comes from the reference code: tapping a suggestion in the Vercel chatbot sends it at once and never fills the input, and on a phone the suggestions form a horizontally scrolling row (primary, the project's source: [suggested-actions.tsx](https://github.com/vercel/chatbot/blob/main/components/chat/suggested-actions.tsx)). For a read-only shell whose commands take no arguments the researcher favours the same tap-to-run, echoing the command into the transcript as if typed, with fill-the-input kept for commands that take an argument, and with the entries of a listing made tappable (inference).

A phone keyboard lacks Tab, Esc, the arrows and Ctrl. Native terminal apps add a row for them (recalled, as in the table). The researcher's inference for a read-only web shell is that only history, completion and clear need on-screen controls, because a real `<input>` already has caret movement through the system's own gestures. Touch-target minimums are 44 by 44 pt from Apple and 48 by 48 dp from Material, read here through secondary sources (community: [Deque](https://dequeuniversity.com/rules/attest-ios/1.0/touch-target-size), [bjango](https://bjango.com/articles/interactiondensity/)) and read from primary pages in the earlier report (`2026-11-18-mobile-web-game-controls.md`); WCAG 2.2's own minimum is 24 by 24 CSS px (primary: [Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). The probe's input was 44 px tall.

## Ordinary HTML is the accessible buffer and the crawlable page

### Real terminals stop reading output aloud after 20 rows

xterm.js and VS Code both concluded that a live stream of terminal output is a poor way to read it. xterm.js's accessibility manager stops announcing after 20 rows and substitutes a localisable message saying there is too much output, clears its live region on every keypress and on blur, sends process output to an assertive live region, and keeps a parallel DOM tree of list items because its rows may be drawn on a canvas; comments in the source admit a race when the user types while data streams and that the prompt is not read out after a command runs (primary: [AccessibilityManager.ts](https://raw.githubusercontent.com/xtermjs/xterm.js/master/src/browser/AccessibilityManager.ts), [xterm.d.ts](https://raw.githubusercontent.com/xtermjs/xterm.js/master/typings/xterm.d.ts); 2019 design document: [xterm.js wiki](https://github.com/xtermjs/xterm.js/wiki/Design-Document:-Screen-Reader-Mode)). VS Code gives screen-reader users a separate navigable view: ⌥F2 opens the terminal buffer in its Accessible View for reading line by line, and ⇧⌘O jumps between commands (primary: [VS Code accessibility](https://code.visualstudio.com/docs/configure/accessibility/accessibility)). Secondary sources date that buffer to about version 1.75 and say it is built on the editor component (community: [a11y-paradise](https://a11y-paradise.onrender.com/glossary/69b2bd8c69b0b553872ae6c0), [vscode-docs mirror](https://source-hub.etos-pro.ru/microsoft/vscode-docs/commit/e06923da5344162e4fbbb7156a40d1b4fbc12429)). The researcher's inference for a page whose content is the transcript: make the transcript itself that navigable view, plain headings, lists and links in document order, so that an announcement only points at content and never carries it.

### Announce one line and leave the output to be read as a document

`role="log"` is an implicit polite, non-atomic live region and must have an accessible name (primary: [MDN, log role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/log_role), last modified 2025-06-23). The working rules come from practitioners: the region must exist, empty, before content is injected; content present at load is deliberately not announced; a region created and filled in the same moment generally fails; and many regions speaking at once are as bad as none (community: [TetraLogical](https://tetralogical.com/blog/2024/05/01/why-are-my-live-regions-not-working/), 2024-05-01; [Scott O'Hara](https://www.scottohara.me/blog/2022/02/05/are-we-live.html), 2022). Support differs by browser and screen reader because the specifications leave the behaviour open (community: [TetraLogical](https://tetralogical.com/blog/2024/05/01/why-are-my-live-regions-not-working/)). a11ysupport.io lists `role="log"` as partial, but its table did not render for the researcher, and no current results for VoiceOver on iOS or TalkBack were found (community: [a11ysupport.io](https://a11ysupport.io/tech/aria/log_role)). A live region speaks text, not structure: the headings, lists and links in an inserted block arrive as one string (recalled).

WCAG draws the line that fits a command's output. Under 4.1.3 a list of search results is not a status message, while a summary such as a count of results is; `role="status"` and `role="log"` are sufficient techniques; and a change that moves focus is a change of context that falls outside the criterion (primary: [Understanding 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)). The pattern the researcher derives is inference: append each command's output to the transcript as ordinary semantic HTML, outside any live region, and write a one-line summary into a single visually hidden `role="status"` element that was empty at load. Focus stays in the input, each output block starts with a heading so heading navigation reaches it, and only a command that replaces the view moves focus, to the new heading. The old terminal does the opposite: its whole log is one `aria-live="polite"` region (read from the repository for this report: `src/components/terminal/ShellView.tsx`).

### No autofocus, a real label, and commands that are links or buttons

MDN lists what `autofocus` does to a page whose control comes after its content. A screen reader is taken to the control without warning and announces nothing that precedes it, the page can scroll on load, a touch device can raise its keyboard, and a sighted visitor on a small screen misses the same context; a URL fragment that targets an element takes precedence over the attribute (primary: [MDN, autofocus](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/autofocus), modified 2026-04-17; [HTML Standard](https://html.spec.whatwg.org/multipage/interaction.html#the-autofocus-attribute)). The researcher adds that a script `focus()` on mount does the same harm (inference). For a page whose prompt is its last element, autofocus would start every such visitor at the end of the portfolio. By WebKit's focus policy it would not raise the iPhone keyboard either, though that was not verified for `autofocus` on iOS 26 or 27.

The prompt needs a real label, because the prompt glyph is not one (WCAG 3.3.2, recalled wording); a visually hidden `<label>` satisfies it and hints attach through `aria-describedby` (inference). A form with one text input submits on Enter natively (recalled; the probe's form did). Commands that can be run without typing must be real controls, and the division the researcher proposes follows what crawlers can use (inference). Google discovers links only from `<a>` elements with an `href` (primary: [Google, JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)), so a command that leads to a section is an `<a href="#projects">`, which works without JavaScript, and a command with no destination, such as clear or a theme switch, is a `<button type="button">`. With JavaScript the page can intercept the link, echo the command into the transcript and keep the URL fragment in step. The ARIA Authoring Practices have no terminal pattern (recalled).

### Animation, ASCII art and small type: keep the text real

A typewriter effect that builds text by script fails three audiences at once (inference): inside a live region every mutation can queue a fragment of speech, outside one a screen-reader user who arrives early reads half a sentence, and a crawler or a visitor without JavaScript gets nothing. xterm.js caps and clears its live region for the first of those reasons (primary: [AccessibilityManager.ts](https://raw.githubusercontent.com/xtermjs/xterm.js/master/src/browser/AccessibilityManager.ts)). The researcher's pattern is inference: the full text is in the prerendered HTML; the animation only reveals it visually, for example with a stepped `clip-path`, and never with `visibility: hidden` or `display: none` on the real text, which would take it out of the accessibility tree; it runs only under `prefers-reduced-motion: no-preference` and only once a script has marked the page as scripted; and the sequence stays under about 5 s or can be skipped. No test data on `clip-path` reveals with screen readers was found. A boot sequence does not belong in a `role="log"` (inference), where content present at load is not announced (community: [TetraLogical](https://tetralogical.com/blog/2024/05/01/why-are-my-live-regions-not-working/)).

H86 accepts ASCII art that is marked up as an image with an equivalent text alternative, or that has a text alternative immediately before or after it, and suggests a skip link when the art is not marked as an image. Its example puts `role="img"` and `aria-label` on the container, and it does not mention `aria-hidden` (primary: [H86](https://www.w3.org/WAI/WCAG22/Techniques/html/H86)). The researcher's reading is inference: decorative art, such as initials beside an `<h1>` that carries the name, takes `aria-hidden="true"`; art that depicts something takes `role="img"` with a label; never both. The facts beside a system-information banner belong in a real `<dl>`, and borders in CSS, not in box-drawing characters. Reflow treats the two halves differently: the art falls under the exception for content whose meaning would be lost, the facts do not, and the exception covers only the part that needs it (primary: [Understanding 1.4.10](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)).

On type, the one measured fact is that the old terminal's output is 11 px against a 16 px prompt row. The researcher's guidance for monospace body text is 16 px or more on phones, a line height of 1.5 or more and a measure of roughly 70 to 80 characters, wrapped; no source on monospace readability was fetched, so this is judgment (inference). Terminal palettes are a known contrast risk: xterm.js and VS Code ship a `minimumContrastRatio` setting that adjusts colours to 4.5 for AA or 7 for AAA (primary: [xterm.d.ts](https://raw.githubusercontent.com/xtermjs/xterm.js/master/typings/xterm.d.ts), [VS Code accessibility](https://code.visualstudio.com/docs/configure/accessibility/accessibility)). Forced-colours mode and reader modes strip author colours, and reader modes drop CSS-generated text, so meaning cannot ride on colour or on a pseudo-element (community, 2021: [Sara Soueidan](https://sarasoueidan.com/blog/tips-for-reader-modes/)).

### Crawlers, reader modes and no-JavaScript visitors read only the HTML

Google renders JavaScript with an evergreen Chromium but can queue the render, says prerendering remains a good idea because not all bots run JavaScript, and does not interact with a page, so content must be present without clicking, typing or scrolling (primary: [Google, JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics), [Google, lazy loading](https://developers.google.com/search/docs/crawling-indexing/javascript/lazy-loading)). The best measurement of AI crawlers is two years old. Vercel and MERJ reported on 2024-12-17 that none of the major AI crawlers rendered JavaScript: GPTBot at 569 million fetches a month, ClaudeBot at 370 million (it fetched JavaScript files in 23.84% of its requests without running them) and PerplexityBot at 24.4 million, while AppleBot and Googlebot did render (community, a vendor's measurement: [Vercel](https://vercel.com/blog/the-rise-of-the-ai-crawler)). No statement from OpenAI, Anthropic or Perplexity in 2025 or 2026 was found.

Reader modes have no published criteria from Apple. Community guidance is to put the core content in an `<article>` with its headings inside, to expect CSS-generated text to be dropped, and to keep non-core content out with `hidden` (community, 2021: [Sara Soueidan](https://sarasoueidan.com/blog/tips-for-reader-modes/)). Safari Reader is reported to weigh content length and on-screen visibility when it activates and to choose the title by nearness to the top of the article and likeness to `document.title` (community: [ctrl.blog, content](https://ctrl.blog/entry/browser-reading-mode-content), [ctrl.blog, metadata](https://www.ctrl.blog/entry/browser-reading-mode-metadata)), and there are reports that `<code>` inside `<p>` can disable it (community: [WebKit bug 225609](https://bugs.webkit.org/show_bug.cgi?id=225609), [Mathias Bynens](https://mathiasbynens.be/notes/safari-reader)). Firefox's Reader View scores the text length of `<p>` and `<pre>` blocks through Readability.js (recalled; thresholds not re-read). One researcher adds that a transcript rendered by script may not be recognised as an article at all (recalled).

For this site the consequences are the researcher's inferences, and they agree with one another. The static export already prerenders the page, so everything that matters goes into that HTML, linked with `<a href>`, and nothing that matters needs a typed command. The profile sits in `<main><article>` under an `<h1>`; the command form and the terminal chrome stay outside the article, or `hidden` until script runs. Hydration must not replace the prerendered sections with an empty transcript, because Google indexes the rendered DOM and the AI crawlers read the raw HTML. Output that only a typed command produces is invisible to every crawler, which is acceptable for extras alone. The generated `llms.txt` and `agents.md` complement the static HTML and do not replace it.

The layout held: on every focus the prompt rested on the bottom of the visible area with no script involved. Several things went wrong around it, in the page's own script and styles. Each was fixed and measured again. These are first-hand observations on one simulated phone, and the explanations offered for them are the measurer's inference.

Some of these extend findings above. The first shows that the viewport's reported position is no better for working out a scroll than for pinning a bar: the probe had already logged `window.scrollY` at 310 while `pageTop` still read 0. The rows on the hidden input agree with the source reading that `preventScroll` suppresses Safari's reveal, and add two things: with the reveal suppressed nothing else moves the page, and the reveal comes back at the first key typed if the field is out of view. That the click handler mattered fits a known rule, that iOS sends a click only to an element it counts as clickable (recalled; React sets an empty click handler on such elements for this reason), but the link to the keyboard is inference. The `<hr>` fault has no source, and no WebKit bug was searched for. The lesson for a hidden input is the same as for a visible one: Safari places a field it can see, and fights a page over one it cannot.

With the fixes in, the final build was taken through each case again: reading, the jump to the prompt, focus, a typed command, a command tapped with the keyboard closed and with it open, a line completed by tapping, and two full-screen programs, one of them taking typed input. In each case the prompt, or the program's input, rested on the bottom of the visible area, directly above Safari's bar when the keyboard was open, and nothing moved once it had settled. Screenshots are in `minimal-terminal-shots/final/` in the session notes.

## Conclusion

The research changes what kind of problem the input bar is. The old terminal treated the keyboard as geometry to be tracked: fit a frame to the visual viewport and the input lands on the keyboard. Every surveyed project that works this way, from jQuery Terminal in 2024 to chat applications this month, reports faults of the kind the owner describes, and the measurements offer a reason that refining the script would not remove them: its numbers arrive late, one of them is unusable, and the last 100 pt belong to Safari. The layout that held is the one that asks Safari for nothing. On this evidence, being anchored to the keyboard is something a page gets by being an ordinary document and loses by trying to enforce it.

The three questions in the brief also turn out to have one answer. A scrolling document whose content is in the static HTML and whose last element is a visible input is what Safari's focus code is written around, what its toolbar collapses for, and what a screen reader, a crawler, a reader mode and a visitor without JavaScript all read. The terminal becomes styling plus three small behaviours: append, scroll by the visual viewport, announce one line. What that structure gives up is a prompt that stays on screen while the visitor reads back, and the evidence on the middle ground, a bar that is sticky only while the keyboard is closed, is a single observation that sticky behaved in that state. The weakest part of the case is its breadth: one simulated phone, one iOS version, and an owner's fault the Simulator did not show. Almost every row below asks for the same thing, the probe page on a real iPhone on iOS 26 and iOS 27.
