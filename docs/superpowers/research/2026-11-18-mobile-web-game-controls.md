# Dragon world on phones: research (2026-11-18)

**iPhone withholds the locks Android grants.** Research report, 2026-11-18. Evidence for the mobile-mode design of
`/world` (`docs/superpowers/specs/2026-11-18-mobile-design.md`); it makes no product decisions.

As of November 2026 a web page cannot lock orientation, enter element fullscreen or vibrate on an iPhone, while Android Chrome allows all three once the player has tapped and the page is fullscreen. Measured in the iOS 26.5 Simulator (iPhone 17), `screen.orientation.lock`, `document.fullscreenEnabled` and `navigator.vibrate` are all `undefined` in Safari and in a Home Screen web app, and a landscape Safari tab gives the page only **874×338 CSS px (874×292 with two or more tabs open)** against **874×402** when installed. A "native feel" on iPhone therefore comes from four things a page does control: a rotate prompt or a portrait layout, a layered gesture lock-down (which held against pinch, double-tap, long-press, pull-to-refresh and the edge back-swipe in the Simulator), a layout sized from the visual viewport at run time, and controls built on Pointer Events over one `touch-action: none` surface. The control conventions are well settled: a base about 100 px across with 50 px of travel, a radial dead zone of 0–20%, and hit zones far larger than the drawn art. On performance, iPhone Safari runs `requestAnimationFrame` at 60 Hz by default and 30 Hz in Low Power Mode, reports 4 cores on every iPhone (so a pool sized to `hardwareConcurrency` holds 120–200 MB of the site's bake workers), and gives pages no memory, thermal or battery API at all. The repository's existing Puppeteer already synthesises trusted multi-touch, safe-area insets, orientation and tab visibility in Chromium, but no emulator shows Safari's toolbars, system gestures, memory kills or heat. Nothing here needs response headers or cross-origin isolation, so the static GitHub Pages export is not a constraint. The Simulator results need confirming on a real iPhone, and iOS 27 was not measured.

**How to read the evidence.** Each claim links to its source. "Primary" means a spec, vendor documentation, vendor source code, release notes or a vendor engineer's comment in a bug tracker. "Community" means a forum, blog, third-party table or bug reporter. "Recalled" means the researcher cited a canonical URL from memory without re-reading it in this session. "Inference" marks reasoning by the researchers, not a sourced fact. Two kinds of first-hand measurement have no URL: results **measured in the iOS 26.5 Simulator (iPhone 17)** by the coordinating session (Xcode 27.2, runtime 23F77, Safari 26.5, a probe page with the site's own viewport tag `width=device-width, initial-scale=1, viewport-fit=cover`, synthesised touches), and **local Puppeteer probes** run against the repository's installed Puppeteer 25.0.4 and headless Chrome 148. Browser versions in play: Safari 27.0 shipped on 2026-09-14 with iOS 27 ([Safari 27 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-27-release-notes.md)); caniuse's current rows are Chrome for Android 157, Firefox for Android 160, Samsung Internet 31 and Safari on iOS 27.2 ([caniuse](https://caniuse.com/screen-orientation)), while Chrome's version-history API reports 159 as stable ([VersionHistory API](https://versionhistory.googleapis.com/v1/chrome/platforms/mac/channels/stable/versions?pageSize=1)).

## One touch-action surface and Pointer Events carry the whole control scheme

### Pointer Events give one captured pointer per finger; the cancel path is mandatory

Pointer Events have shipped in Safari since 13 and Chrome since 55 (recalled: [caniuse](https://caniuse.com/pointer)). The spec gives touch input **implicit capture**: the browser behaves "exactly as if setPointerCapture was called on the target element" before `pointerdown` listeners run, so a finger that slides off a control keeps reporting to it, and other elements get no `pointerenter` until capture is released (primary: [W3C Pointer Events](https://w3c.github.io/pointerevents/)). Each finger has its own `pointerId`, and only the first touch is `isPrimary`; the second thumb on a boost button has `isPrimary === false`, so a multi-touch scheme must never filter on it (primary: [W3C Pointer Events](https://w3c.github.io/pointerevents/)). An explicit `setPointerCapture` fails silently unless the pointer is in its active-buttons state and throws `NotFoundError` for an unknown id (primary: [W3C Pointer Events](https://w3c.github.io/pointerevents/)). One cross-browser bug report shows that when a parent captures after a child received implicit capture, later moves were not retargeted to the parent, which argues for listening on the one surface that owns all controls (community: [w3c/pointerevents #327](https://github.com/w3c/pointerevents/issues/327)).

The spec says panning and zooming "cannot be suppressed by canceling a pointer event"; `touch-action` is the required mechanism, and `touch-action: none` must sit on the element under the finger because the browser intersects the values of the touched element and its ancestors when the gesture starts (primary: [W3C Pointer Events](https://w3c.github.io/pointerevents/); [MDN touch-action](https://developer.mozilla.org/en-US/docs/Web/CSS/touch-action)). iOS Safari has supported `touch-action: none` since 13; before that only `auto` and `manipulation` worked (community table: [caniuse](https://caniuse.com/css-touch-action)).

`pointercancel` is the event that leaves a joystick stuck. The spec requires it when the browser opens a modal dialog or menu, when the pointer is then used for panning or zooming, or when drag-and-drop starts, and allows it on orientation change, on more touches than the device supports and on palm rejection; it is never cancelable (primary: [W3C Pointer Events](https://w3c.github.io/pointerevents/)). Mobile Safari fires it whenever it takes a touch over, as one iPadOS 17 report of a stuck drag shows (community: [vkurko/calendar #689](https://github.com/vkurko/calendar/issues/689)). The researchers infer that system-edge gestures, app switching and alert sheets also arrive as cancels; no Apple document lists them. A local Puppeteer probe confirmed that a CDP `touchCancel` produces `pointercancel` for every active pointer, so the release path can be pinned by a test.

The low-latency extras do not matter for a joystick. `pointerrawupdate` is unsupported in Safari through 27.3 and iOS Safari through 27.2 ([caniuse](https://caniuse.com/mdn-api_element_pointerrawupdate_event)), and MDN says it "is not more precise in space or time" than `pointermove` (primary: [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Element/pointerrawupdate_event)). `getCoalescedEvents()` reached Safari in 18.2, with a launch bug in which coalesced events lacked `pointerId` and `target` (community: [Flutter engine PR 56719](https://github.com/flutter/engine/pull/56719)); whether that bug persists in 26/27 is unknown. Recent Safari changes are small: fractional pointer coordinates in 26.2 ([WebKit 26.2](https://webkit.org/blog/17640/webkit-features-for-safari-26-2/)), and in 27.0 `preventDefault()` on `pointerdown` now suppresses the compatibility mouse events ([WebKit 27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/)).

> **Measured in the iOS 26.5 Simulator (iPhone 17).** `PointerEvent.prototype.getCoalescedEvents` is a function; `navigator.maxTouchPoints` is 5; `(pointer: coarse)` and `(hover: none)` match and `(any-hover: hover)` does not. Pointer events were still delivered (down and up counted) when a non-passive `touchstart` listener called `preventDefault()`, so the touch-event lock-down described later does not starve Pointer Events. Needs confirming on a real device.

### Passive listeners are why preventDefault silently fails on the document

`touchstart` and `touchmove` listeners on `window`, `document` or `body` are passive by default in Chrome since 56, so `preventDefault()` there is ignored unless the listener is registered with `{ passive: false }`; Chrome's stated order of preference is `touch-action` first and a non-passive listener "only as a last resort" (primary: [Chrome scrolling intervention](https://developer.chrome.com/blog/scrolling-intervention)). WebKit made the same root targets passive in iOS 11.3 and closed the regression report as intended ([WebKit bug 182521](https://bugs.webkit.org/show_bug.cgi?id=182521)); a `touchmove` listener added inside `touchstart` cannot stop a scroll already under way, so non-passive handlers must be bound up front ([WebKit bug 184250](https://bugs.webkit.org/show_bug.cgi?id=184250)). The design consequence is a split of duties: Pointer Events for game input, and touch events used only as a blocker.

### Joystick libraries converge on a 100 px base, 50 px travel and a small radial dead zone

| Library | Base and travel | Dead zone | Placement modes | Other defaults |
|---|---|---|---|---|
| nipplejs ([README](https://github.com/yoannmoinet/nipplejs), primary) | `size` 100 px; nub 50% of it, so 50 px travel | `threshold` 0.1 (direction events only) | `dynamic` (appears at each touch), `semi` (reuses the stick within `catchDistance` 200 px, else makes a new one), `static`; `follow` drags the base once the thumb passes the edge | `fadeTime` 250 ms, `restOpacity` 0.5, `dataOnly` emits events with no DOM |
| Godot `VirtualJoystick` ([docs](https://docs.godotengine.org/en/latest/classes/class_virtualjoystick.html), primary) | `joystick_size` 100, `tip_size` 50, `clampzone_ratio` 1.0 | `deadzone_ratio` 0.0 (left to action dead zones) | `FIXED` (default), `DYNAMIC`, `FOLLOWING` | returns to rest on release |
| Unity On-Screen Stick ([manual](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.11/manual/OnScreen.html), primary) | "Movement Range", 50 in the worked example | none built in | static origin or dynamic origin at the press point | On-Screen Button is a pure hold: 1 on down, 0 on up |
| Phaser rex plugin ([docs](https://rexrainbow.github.io/phaser3-rex-notes/docs/site/virtualjoystick/), primary) | `radius` 100 in the example | `forceMin` 16 px in the example (16%) | `fixed: true` | emulates cursor keys; `8dir`, `4dir` |

For dead-zone shape the standard reference says axial (per-axis) zones snap input to the cardinals and feel bad for analog steering; use a **scaled radial** zone that is zero inside and remaps magnitude from [dead zone, 1] to [0, 1], with typical values "somewhere between 0.1 to 0.2" for physical sticks ([Game Developer](https://www.gamedeveloper.com/business/doing-thumbstick-dead-zones-right)). None of these libraries applies a response curve by default. No published study of optimal touch-stick radius or dead zone was found; every number is a library default or practitioner convention. Community playtests favour a floating stick in a left-half zone with a faint resting "ghost", one project reporting thumb drift with a fixed stick during fast play (community: [me_rpg #16](https://github.com/jbogaardt/me_rpg/issues/16)), and Apple's guidance is to "show a virtual thumbstick wherever the player lands their thumb instead of a static thumbstick position" (primary: [Apple HIG, Game controls](https://developer.apple.com/design/human-interface-guidelines/game-controls)).

The researchers' starting numbers, all inference to tune on a device, are a base of 100–120 CSS px, travel 50–60, a dead zone of about 6 px (8–15%), a floating origin in the left 40–50% of the screen, and base-follow once the thumb passes roughly 1.0–1.3× travel. They also note that a virtual stick has no sensor noise, so smoothing belongs in the dragon's turn-rate response, not in the stick.

### Three steering mappings, each with a known cost

No source compares steering schemes for overhead flight on touch; this is the least-evidenced part of the brief. The options the notes set out are these. **Absolute steering** (stick angle is the desired heading, the dragon turns toward it at its own turn rate) matches an unrotated overhead camera and lets stick magnitude stand in for boost, but it differs from today's keyboard model and needs a tie-break for 180° flicks. **Relative steering** (stick x is turn rate) reuses the keyboard path with no simulation change, but becomes disorienting "tank control" when the dragon flies down-screen. **Drag-to-steer** (the dragon heads toward the finger) needs one thumb and no UI, but the finger covers the destination and boost needs a second gesture. **Tap-to-fly-to-point** is accessible but indirect. slither.io, the closest shipped analogue for a long serpentine body seen from above, ships three of these side by side: slide anywhere, a visible lower-left stick with hold-right-side to boost, and an invisible stick with a heading arrow drawn on the snake; a reviewer found the visible stick most precise and slide-anywhere least reliable (community: [Pocket Gamer](https://www.pocketgamer.com/slither-io/which-control-scheme-is-the-best-in-slither-io)).

### Buttons: platform minimums are 44 pt and 48 dp; game guidance asks for much more

| Source | Minimum | Notes |
|---|---|---|
| Apple HIG, game controls (primary: [HIG](https://developer.apple.com/design/human-interface-guidelines/game-controls)) | 44×44 pt for frequent controls; 28×28 pt for menus | Respect safe areas, Home indicator and Dynamic Island; menus at the top |
| Android accessibility (primary via search: [Android Help](https://support.google.com/accessibility/android/answer/7101858)) | 48×48 dp (about 9 mm), 8 dp apart | Hit area may exceed the visible element |
| WCAG 2.2 (primary: [SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)) | 24×24 CSS px (AA); 44×44 (AAA, SC 2.5.5) | |
| Xbox Accessibility Guideline 107, dated 2026-11-13 (primary: [XAG 107](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/107)) | Phones 15×15 mm; tablets 24×24 mm | Adjustable size, spacing and position; preset layouts |

Apple's TouchController session explains the reason for oversized hit zones: players cannot feel where a finger is relative to a drawn control, so its thumbstick takes a half-screen collider (`.leftSide`/`.rightSide`) and can hide until pressed (primary: [WWDC26 session 358](https://developer.apple.com/videos/play/wwdc2026/358/)). Native press-timing conventions, all recalled and not web-specific, are a 0.5 s long-press with 10 pt of allowed movement on iOS ([Apple](https://developer.apple.com/documentation/uikit/uilongpressgesturerecognizer/minimumpressduration)) and on Android a 400 ms long-press, 100 ms tap timeout, 300 ms double-tap timeout and 8 dp touch slop ([Android ViewConfiguration](https://developer.android.com/reference/android/view/ViewConfiguration)).

The guidance pulls two ways on activation. XAG 107 says "Control activations should occur on touch-end or mouse-up events" so a player can slide off to cancel, with an exception where down-activation is essential, and asks games to avoid or offer alternatives to prolonged holds, simultaneous presses and tilt ([XAG 107](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/107)); the Game Accessibility Guidelines say the same about holds and simultaneous actions ([GAG](https://gameaccessibilityguidelines.com/full-list/)). Apple recommends folding functions into one control, and its Dredge example sprints when stick magnitude exceeds **0.8** with a halo drawn on the stick, shows context buttons only while usable, and auto-dismisses a pop-up choice after **3.0 s** ([WWDC26 session 358](https://developer.apple.com/videos/play/wwdc2026/358/)). Applied to boost, brake and land, the options are: boost as a held button (mirrors the keyboard, but is a hold and a second simultaneous finger), boost as a toggle, boost on stick deflection past a threshold (one-handed, no extra button), or slither.io's hold-the-other-half; land as a permanent button or as a context button that appears only over a tower; brake as a held button or folded into low stick deflection. The researchers' starting sizes, as inference: a primary action of 72–80 CSS px near the lower-right thumb rest, secondaries of 56–64 px on an arc 12–16 px apart, a 44 px Leave/Pause in a top corner, hit areas 8–12 px beyond the art, and release hysteresis of 12–16 px beyond the drawn radius. They also advise against long-press as a game verb on iOS, because about 500 ms is where the system callout lives. Because touch pointers are captured, slide-on between buttons only works if the game hit-tests pointer coordinates itself or releases capture; Godot exposes this as `passby_press` ([Godot TouchScreenButton](https://docs.godotengine.org/en/stable/classes/class_touchscreenbutton.html)).

### Haptics exist on Android only

`navigator.vibrate(ms)` or a pattern array works in Android Chrome; it is not Baseline (primary: [MDN Vibration API](https://developer.mozilla.org/en-US/docs/Web/API/Vibration_API)). Chrome gates it on **sticky** user activation, which once set never resets for the frame, and blocks cross-origin iframes, so a page can vibrate from game logic (a landing, say) any time after the first tap ([W3C implementation report](https://w3c.github.io/vibration/reports/implementation.html); [Chrome user activation](https://developer.chrome.com/blog/user-activation)). Firefox for Android accepts the call and does nothing ([W3C implementation report](https://w3c.github.io/vibration/reports/implementation.html)). WebKit has never shipped it ([WICG web-haptics](https://github.com/WICG/web-haptics)), and the Safari 27.0 notes add no haptics API ([WebKit 27.0](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/)).

> **Measured in the iOS 26.5 Simulator (iPhone 17).** `typeof navigator.vibrate` is `undefined`, in Safari and in a Home Screen web app.

The iOS workaround was the `<input type="checkbox" switch>` control, shipped in Safari 17.4 ([WebKit](https://webkit.org/blog/15054/an-html-switch-control/)): a script clicked a hidden switch's label and Safari played its native tick. Library authors report that Apple closed the scripted path in iOS 26.5; now only a real finger tap on a real switch or label fires the tick, once per tap, and multi-tick patterns play only their first tick (community, untested on devices by those projects: [tijnjh/ios-haptics](https://github.com/tijnjh/ios-haptics); [haptics.kushagragolash.dev](https://haptics.kushagragolash.dev/)). That path cannot fire from a held, moving or captured pointer, nor from a game event, so it reaches at most discrete DOM menu buttons. A standard is far off: WICG Web Haptics proposes `navigator.playHaptics(effect, intensity)` with six semantic effects, was adopted into WICG in April 2026, and names no shipping implementation ([WICG web-haptics](https://github.com/WICG/web-haptics)). Gamepad rumble (`vibrationActuator`) works in Chrome 68+ but not in iOS or iPadOS Safari ([WebKit bug 263022](https://bugs.webkit.org/show_bug.cgi?id=263022)). No authoritative guidance on durations exists; the researchers suggest, as inference, discrete pulses of 8–12 ms for presses and 20–30 ms for a landing, with a user toggle, which the Game Accessibility Guidelines also ask for ("Include toggle/slider for any haptics", [GAG](https://gameaccessibilityguidelines.com/full-list/)).

### Tilt steering is possible on both platforms but must be opt-in

On iOS, `DeviceOrientationEvent.requestPermission()` must be called from a UI event on HTTPS; it resolves to `"granted"` or `"denied"` and throws `NotAllowedError` without transient activation; where the function is absent, no permission is needed (primary: [MDN](https://developer.mozilla.org/en-US/docs/Web/API/DeviceOrientationEvent/requestPermission_static)). Chrome on Android delivers the events with no prompt ([Chromium issue 40094424](https://issues.chromium.org/issues/40094424)). The grant's lifetime on iOS is unsettled: old forum reports say Safari remembers the answer across reloads (community: [Apple Developer Forums 128376](https://developer.apple.com/forums/thread/128376)), and a 2026 probe project still lists it as unresolved (community: [issue 169](https://github.com/paulgibeault/paulgibeault.github.io/issues/169)). WCAG 2.5.4 (Level A) requires that motion-operated functions also work through ordinary controls and that motion response can be turned off ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/motion-actuation.html)), so tilt can only ever be an optional extra scheme. `alpha`, `beta` and `gamma` are defined in the device's portrait frame whatever the screen rotation (recalled: [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Device_orientation_events/Orientation_and_motion_data_explained)), so landscape needs an axis swap keyed on `screen.orientation.angle`. The notes' parameters are inference, not device-tested: roll from the gravity vector to avoid Euler flips when the phone is held upright, a neutral pose captured on enable, a dead zone of ±3–5°, full lock at ±25–30°, and a low-pass filter with a 50–100 ms time constant.

> **Measured in the iOS 26.5 Simulator (iPhone 17).** `typeof DeviceOrientationEvent.requestPermission` is `function`; `screen.orientation.type/angle` read `portrait-primary 0` and `landscape-primary 90`. The prompt itself and the grant's lifetime were not exercised.

The Gamepad API works in iOS Safari from 10.3 and in Chrome for Android ([caniuse](https://caniuse.com/gamepad)), so a Bluetooth controller is a third input device; `gamepadconnected` fires on first button press if the pad was already paired ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Gamepad_API/Using_the_Gamepad_API)).

### Orientation lock: fullscreen first on Android, nothing on iPhone

The spec lets a browser restrict `lock()` to fullscreen documents and says installed apps should be in the `fullscreen` display mode; it also says an app for which one orientation is essential "must advise the user of the orientation requirements" (primary: [W3C Screen Orientation](https://www.w3.org/TR/screen-orientation/), Working Draft of 2026-11-17). Chromium's source shows the Android rule exactly: the lock fails with `ERROR_FULLSCREEN_REQUIRED` unless the WebContents is fullscreen **or** its display mode is `kFullscreen`; the promise stays pending until the orientation actually matches; leaving fullscreen unlocks; and any navigation unlocks ([screen_orientation_provider.cc](https://raw.githubusercontent.com/chromium/chromium/main/content/browser/screen_orientation/screen_orientation_provider.cc)). Chrome's error names differ from the current draft: it throws `SecurityError` ("The page needs to be fullscreen...") where the draft says `NotAllowedError`, `NotSupportedError` where the device cannot lock, and `AbortError` when superseded ([lock_orientation_callback.cc](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/modules/screen_orientation/lock_orientation_callback.cc)). The safe call order is therefore tap, `await requestFullscreen()`, then `await lock('landscape')`, repeated after every return to fullscreen, with any rejection treated as "no lock" (inference from the source). Whether the lock rotates an Android phone whose auto-rotate is off has no primary source.

On iOS, Safari 16.4 shipped only `type`, `angle` and `onchange`; `lock()` and `unlock()` stayed experimental ([WebKit 16.4](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/)). Apple's Marcos Cáceres said in June 2023 that the lock will not work in Safari on iPad, "may work" as a Home Screen web app, and is blocked on iPhone by the lack of element fullscreen; a 2024 question about enabling the flag got no reply ([WebKit bug 257695](https://bugs.webkit.org/show_bug.cgi?id=257695)). Neither the Safari 26.0 post nor the 27.0 notes mention it ([WebKit 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/); [Safari 27 notes](https://developer.apple.com/documentation/safari-release-notes/safari-27-release-notes.md)). caniuse marks iOS Safari 16.4–27.2 as "supported" ([caniuse](https://caniuse.com/screen-orientation)), which reflects the interface existing, not locking.

> **Measured in the iOS 26.5 Simulator (iPhone 17).** `typeof screen.orientation.lock` is `undefined`, not a function that rejects, in Safari and in a Home Screen web app. This settles the caniuse ambiguity for 26.5: feature-detect with `typeof screen.orientation?.lock === "function"`. Apple's "may work as a Home Screen web app" did not hold here. Needs confirming on a real device and on iOS 27.

With no lock, the notes describe three patterns for iPhone. A **rotate overlay** shown in portrait is the cheapest and matches the portals: CrazyGames takes the orientation as submission metadata and prompts users itself ([CrazyGames technical requirements](https://docs.crazygames.com/requirements/technical/)). Its weakness is the iPhone's own Portrait Orientation Lock, under which the page never turns, so the overlay needs a way out. A **CSS-rotated landscape** (a wrapper turned 90° while the viewport is portrait) plays with rotation lock on, and one developer in the WebKit tracker reports building such a fallback ([WebKit bug 257695](https://bugs.webkit.org/show_bug.cgi?id=257695)); its costs are inferred, not sourced: pointer coordinates must be remapped by hand, safe-area insets stay in portrait terms, and Safari's toolbar, the home indicator and edge gestures stay portrait. A **portrait-capable layout** avoids the question; Poki says "cover the full screen in portrait or landscape, or both for the best experience" ([Poki](https://developers.poki.com/guide/requirements-quality)), and XAG 107 asks games to "Support gameplay in both portrait and landscape" because some players' devices are mounted ([XAG 107](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/107)). In portrait the 16:9 frame fills only the top of the screen, leaving the lower part for controls (inference).

### Fullscreen: Android and iPad yes, iPhone no and no plan

`requestFullscreen({ navigationUI })` needs transient activation and reports exits through `fullscreenchange` on `document`, including exits the user makes ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Element/requestFullscreen)). Safari 16.4 unprefixed the API on macOS and iPadOS, where users leave with "a downward touch gesture" ([WebKit 16.4](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/)); on iPad it shows an overlay button the page cannot remove ([caniuse](https://github.com/Fyrd/caniuse/blob/main/features-json/fullscreen.json)), and Safari 26.0 narrowed an over-broad exit trigger to text-entry focus ([WebKit 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)). For iPhone, WebKit bug 206854 "Add Fullscreen API to iOS" is still NEW and unassigned, last modified 2026-10-30, with no Apple reason or plan ([WebKit bug 206854](https://bugs.webkit.org/show_bug.cgi?id=206854)); the Safari 27.0 notes list only media and visionOS fullscreen fixes ([Safari 27 notes](https://developer.apple.com/documentation/safari-release-notes/safari-27-release-notes.md)). On Android, Back or an edge swipe exits fullscreen and Chrome then drops the orientation lock, so a `fullscreenchange` with no fullscreen element is a natural "pause and show Resume" moment, and the Resume tap supplies the gesture to re-enter (inference; the exit gestures were not sourced). CrazyGames warns that "`Escape` closes fullscreen" and should not be the only pause key ([CrazyGames quality guidelines](https://docs.crazygames.com/requirements/quality/)).

### Installing: the strongest lock on Android, toolbar removal only on iOS

The manifest's `display` falls back along `fullscreen → standalone → minimal-ui → browser`, and `@media (display-mode: …)` reports the mode in use; a `fullscreen` display mode is separate from the Fullscreen API, so `document.fullscreenElement` stays `null` ([MDN display](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/display)). `orientation` sets the default for every top-level context in scope ([MDN orientation](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/orientation)). The notes infer from this that a whole-site manifest with `orientation: landscape` would turn the Recruiter page and terminal sideways on Android, and that a manifest scoped to `/world/` and linked only from that route installs just the game; with `output: 'export'` a static file in `public/` is the simple route, since `app/manifest.ts` lives only at the app root ([Next.js manifest](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/manifest); [Next.js static exports](https://nextjs.org/docs/app/guides/static-exports)).

On iOS and iPadOS, `display: fullscreen` falls back to `standalone`, and `orientation`, `display_override` and `beforeinstallprompt` are unsupported ([firt.dev](https://firt.dev/notes/pwa-ios/)). Since iOS 26, "every website added to the Home Screen opens as a web app" by default and no manifest is required ([WebKit 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)). A bug report says that since iOS 26.1 installed apps show the status-bar area blocking the view where `standalone` plus `viewport-fit=cover` used to draw under it (community: [WebKit bug 301994](https://bugs.webkit.org/show_bug.cgi?id=301994)). Chrome offers its install prompt when the user has tapped once and spent 30 seconds on the page, over HTTPS, with a manifest carrying a name, 192 px and 512 px icons, `start_url` and a `display` of `fullscreen`, `standalone` or `minimal-ui`; the list has no service-worker requirement ([web.dev](https://web.dev/articles/install-criteria)).

> **Measured in the iOS 26.5 Simulator (iPhone 17).** A Home Screen web app gets the whole screen in landscape, 874×402 CSS px, and 402×812 in portrait with the status bar excluded, which is consistent with bug 301994. It still has no orientation lock and no element fullscreen, and it keeps the edge back-swipe on ordinary pages.

On a page that cannot scroll, swiping did not collapse the toolbar (the height stayed 292 px). `screen.width/height` stay 402×874 in landscape. The side insets are symmetrical (62 each) whichever side the Dynamic Island is on. Needs confirming on a real device.

These numbers fill a gap the web sources left open (no Apple description of the iOS 26 toolbar geometry was found) and confirm an inference: toolbar collapse is driven by document scroll, so a locked, non-scrolling game in a Safari tab always gets the small viewport. They also correct two secondary figures. A community table of UIKit safe areas gives the iPhone 17 a 20 pt top inset in landscape and 62/34 pt top/bottom in portrait ([Use Your Loaf](https://useyourloaf.com/blog/iphone-17-screen-sizes/)); Safari's `env()` values differ (top 0 in landscape, and 0 on all sides in portrait Safari). The same table lists iPhone Air at 68 pt side insets and 29 pt bottom in landscape, which is unmeasured here. And Playwright's iPhone 17 landscape descriptor assumes a 756×352 viewport ([deviceDescriptorsSource.json](https://github.com/microsoft/playwright/blob/main/packages/isomorphic/deviceDescriptorsSource.json)), which matches neither measured case.

The arithmetic for hard pixels follows from the measurements (this is calculation, not a sourced figure). At DPR 3 one frame pixel at scale k is k/3 CSS px, so a 400×225 frame needs 225 CSS px of height at 3×, 300 at 4× and 375 at 5×. A one-tab Safari landscape (338 px, or 318 above the home-indicator inset) fits **4×** (533×300 CSS px); with the tab bar (292 px) only **3×** (400×225) fits; the Home Screen web app (402 px) fits **5×** (667×375). The frame is height-limited in all three, leaving side bars of roughly 104–237 CSS px each, wider than the 62 px insets. A 44 pt target is 44 frame pixels at 3×, 33 at 4× and about 26 at 5×, so controls drawn into the frame change physical size with the scale unless they are sized in CSS px.

The units behave as documented: `svh` assumes the browser UI expanded, `lvh` retracted, `dvh` follows it but is throttled, plain `100vh` behaves like the large viewport, and all three shipped in Safari 15.4, Chrome 108 and Firefox 101 ([web.dev](https://web.dev/blog/viewport-units)). iOS 26 made them less trustworthy. WebKit bug 297779, filed 2025-08-22, records `position: fixed` elements shifting about 10 px as the toolbar minimises and `visualViewport.offsetTop` sticking at 24 after the keyboard closes on 26.0; Apple said a fix was coming (2025-09-16) and that `bottom: 0` sitting above the Liquid Glass controls is intentional (2025-10-01); reports of it persisting run to 2026-10-01 on iOS 26.6.1 ([WebKit bug 297779](https://bugs.webkit.org/show_bug.cgi?id=297779); [Apple Developer Forums 800125](https://developer.apple.com/forums/thread/800125)). The notes therefore recommend, as inference, sizing and translating the fixed game layer from `window.visualViewport` on every `resize` and `scroll` event, throttled to one run per frame, with `100dvh` as the no-script fallback, and never making the document taller than the viewport to push the toolbar away. A game with no text input avoids the keyboard, the main trigger for the stuck offset.

On Android, Chrome 135 began extending the viewport under the gesture bar: with `viewport-fit=cover` the page reaches the bottom edge on load with no "chin", `safe-area-inset-bottom` becomes dynamic, and a new `env(safe-area-max-inset-bottom)` gives its maximum; the rollout is by Chrome Variation and small screens only ([Chrome edge-to-edge guide](https://developer.chrome.com/docs/css-ui/edge-to-edge)). Android cutout insets for a normal landscape tab were not sourced.

### Stopping zoom, refresh, selection and callouts takes layers, and the layers held

No single switch locks a page down on iOS. The viewport meta cannot: since iOS 10 "Safari... allows the user to pinch zoom on every page", though the switch is per embedder and an in-app WKWebView may still honour `user-scalable=no` ([WebKit](https://webkit.org/blog/7367/new-interaction-behaviors-in-ios-10/)). Chrome for Android obeys it unless the user has turned on "Force enable zoom" (community: [Stefan Judis](https://www.stefanjudis.com/blog/how-to-enforce-pinch-to-zoom-on-firefox-chrome-on-android)). `touch-action: none` is the main control, but community reports list iOS escapes: multi-finger pans, a pinch begun after a slight one-finger scroll, and Safari's pinch-to-tab-overview firing "occasionally" even with all gesture events cancelled ([WebKit bug 233141](https://bugs.webkit.org/show_bug.cgi?id=233141)). The second layer has the best pedigree: WebKit's Wenson Hsieh confirmed that `preventDefault()` in an active (non-passive) `touchstart` listener suppresses the long-press loupe, which CSS alone has failed to do twice, in iOS 15 and again in July 2025 ([WebKit bug 231161](https://bugs.webkit.org/show_bug.cgi?id=231161)). `-webkit-touch-callout` governs only the callout menu, not the loupe ([WebKit bug 231161](https://bugs.webkit.org/show_bug.cgi?id=231161)), and one unanswered forum post reports it failing on iOS 26.1 (community: [Apple Developer Forums 808606](https://developer.apple.com/forums/thread/808606)). For overscroll, `overscroll-behavior: none` disables pull-to-refresh and the glow in Chrome ([Chrome](https://developer.chrome.com/blog/overscroll-behavior)); iOS lists support from 16.0 but users report bounce and refresh returning in some configurations (community: [TMS forum](https://support.tmssoftware.com/t/pull-to-refresh-again/26279)), and the old `position: fixed` on `body` trick stopped working by 2021 (community: [Bram.us](https://www.bram.us/2016/05/02/prevent-overscroll-bounce-in-ios-mobilesafari-pure-css)). Portals ask for the same basics: CrazyGames requires `user-select: none` on `body` because "double tapping, or pressing and holding can show the magnification tool" ([CrazyGames](https://docs.crazygames.com/requirements/technical/)).

> **Measured in the iOS 26.5 Simulator (iPhone 17), Safari landscape.** The probe's lock recipe was: on `html`/`body`, `height: 100%; overflow: hidden; overscroll-behavior: none; user-select: none` (with the `-webkit-` prefix); `-webkit-touch-callout: none; -webkit-tap-highlight-color: transparent`; `touch-action: none` on a full-viewport `position: fixed; inset: 0` layer; a non-passive `touchstart` `preventDefault()` on that layer (except on buttons and links); `gesturestart/gesturechange/gestureend` `preventDefault()` on `document`; a non-passive `touchmove` `preventDefault()` on `document`; and `contextmenu` and `dblclick` cancelled.
>
> | Gesture | Plain page | Locked page |
> |---|---|---|
> | Two-finger pinch-out | Zoomed (`visualViewport.scale` > 1) | No zoom; `scale` stayed 1.00; 7 gesture events prevented |
> | Double-tap | not measured | No zoom, no `dblclick` |
> | 1.5 s long-press on text | not measured | No selection, loupe, callout or `contextmenu`; pointer down/up delivered, no `pointercancel` |
> | Pull down from the top | not measured | No refresh, no scroll |
> | Swipe from 2 pt inside the left edge | Navigated back (Safari and Home Screen web app) | Did not navigate; no `popstate` even with a pushed history entry |
>
> These are synthesised touches on one simulated device. They need confirming on a real iPhone, in particular the edge swipe, the "scroll then pinch" escape and the tab-overview pinch, none of which the Simulator reproduces faithfully.

The cost of the lock is accessibility: MDN warns that `touch-action: none` "may prevent users from operating the browser's zoom features" and cites WCAG 1.4.4 ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/touch-action)). The notes' answer, a judgment and not a cited ruling, is to scope every part of the lock to `/world` and remove it on leaving, because the App Router keeps `<html>`, `<body>` and `document` listeners alive across client navigations and a leak would lock zoom on the Recruiter page. Cancelling `touchstart` also suppresses the synthesised `click`, so real HTML buttons inside the layer must be excluded (as the probe did) or driven from `pointerup`. `visualViewport.scale !== 1` detects a player who zoomed anyway.

### System gestures cannot be turned off, only avoided and absorbed

No web API disables the back, home or app-switcher gestures. Android's back gesture is an inward swipe from either side edge, and native apps, not pages, can exclude regions from it ([Android gesture navigation](https://developer.android.com/develop/ui/views/touch-and-input/gestures/gesturenav)); its width is a device overlay value, with 24 dp and 30 dp appearing in AOSP and a user sensitivity slider scaling it (low confidence: [AOSP commit](https://android.googlesource.com/platform/frameworks/base/+/771557666d8d%5E%21/)). On iOS, cancelling a `touchstart` within 20 px of a side edge has blocked the back swipe since Safari 13.4 by one account (community: [pqina](https://pqina.nl/blog/blocking-navigation-gestures-on-ios-13-4)) and only "sometimes" by another (community: [Ionic issue 22299](https://github.xay.workers.dev/ionic-team/ionic-framework/issues/22299)). The Simulator result above sides with the first, but a synthesised edge swipe is weak evidence. The notes' edge budget is inference: keep controls about 32 CSS px in from the sides on Android and 20–24 px on iOS, plus the safe-area insets, and keep drag controls off the bottom strip. Absorbing a Back that does fire has three layers on Android: element fullscreen takes the first Back, a `CloseWatcher` (Chrome 126+, absent from iOS Safari through 27.2, [caniuse](https://caniuse.com/mdn-api_closewatcher)) can turn the next into "open the menu", and a `history.pushState` entry made from the tap that starts flight catches the rest. On iOS only the pushState layer exists.

### Pause on hidden, on blur and on a silent stall

The Page Lifecycle states and events are `visibilitychange`, `focus`/`blur`, `pagehide`/`pageshow` with `persisted`, and `freeze`/`resume` (Chrome 68+ only); on mobile, the move to hidden is the last reliably observable one, and `unload` should never be used ([Chrome Page Lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)). iOS is patchier: an open bug filed against iOS 13 records that entering the App Switcher fires no events at all, switching apps fires `blur` and `visibilitychange`, and Safari's tab switcher fires only `blur` ([WebKit bug 206213](https://bugs.webkit.org/show_bug.cgi?id=206213)); it has had no update since 2020. Chrome does not run rAF in background tabs and clamps their timers to once a second (community summary: [Motion](https://motion.dev/magazine/when-browsers-throttle-requestanimationframe)). From this the notes infer a pause rule of "hidden, `pagehide`, `freeze` or `blur`", a clamped frame delta (100 ms, say) with any gap over about 250 ms treated as a pause, a reset of all pointer state on pause because a suspended page never receives `pointerup`, and a tap-to-continue overlay on return, which also supplies the gesture audio needs. How workers behave in hidden tabs on either platform was not sourced; the notes' belief that Chrome keeps dedicated workers running while iOS suspends the whole process is general knowledge.

The Screen Wake Lock API (`navigator.wakeLock.request("screen")`) is Baseline since March 2025, needs HTTPS, works in a top-level page with no header, is released automatically when the page is hidden and must be re-requested on return; requests can be rejected under power-save or low battery ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API)). It is in Chrome 84+ and Safari 16.4+ ([BCD](https://github.com/mdn/browser-compat-data/blob/main/api/WakeLock.json)), and was broken in Home Screen web apps until iOS 18.4 ([Safari 18.4 notes](https://developer.apple.com/tutorials/data/documentation/safari-release-notes/safari-18_4-release-notes.md)). Touch input resets the OS idle timer, so the lock matters only in hands-off moments such as reading a Codex entry (inference).

> **Measured in the iOS 26.5 Simulator (iPhone 17).** `typeof navigator.wakeLock` is `object` in Safari and in a Home Screen web app. A request was not exercised.

## Phones give 30 to 120 frames a second, four reported cores and no gauges

### The frame rate is whatever the phone decides

On iPhone and iPad, page rendering, including rAF, runs at "60Hz by default on ProMotion displays"; a user-facing feature flag can raise it to 120 (primary, 2025-04-02: [WebKit bug 290671](https://bugs.webkit.org/show_bug.cgi?id=290671)). A WebKit commit of 2025-12-23 confirms both that default and that the preferred rate "may be lower than 60fps for low-power mode", its test note verifying callbacks "at around 30fps" ([webkit-changes](https://mail-archive.com/webkit-changes@lists.webkit.org/msg241179.html)); Apple treats the Low Power cap as intentional ([WebKit bug 215745](https://bugs.webkit.org/show_bug.cgi?id=215745)), and no page can override it (community: [GreenSock forum](https://greensock.com/forums/topic/26826-any-way-to-keep-gsap-running-at-60fps-while-mobile-device-is-in-low-power-mode/)). Android Chrome runs rAF at the panel rate, as a report of animations running "really fast" on 120 Hz phones shows (community: [three.js forum](https://discourse.threejs.org/t/120hz-screens-animation-too-fast-issue/39940.md)), and Android may restrict refresh rate in battery saver ([Android frame-rate guide](https://developer.android.com/media/optimize/performance/frame-rate)). No API requests a frame rate ([whatwg/html #5025](https://github.com/whatwg/html/issues/5025)). The loop will therefore see 30, 60, 90 and 120 Hz. The notes infer that the simulation needs a fixed timestep, that a median rAF interval near 33 ms is the only Low Power Mode signal on iOS, and that a 30 fps cap divides evenly into 60, 90 and 120 Hz panels if done by skipping callbacks by timestamp. Whether Safari 27 changed the 60 Hz default was not verified.

### Hard pixels: a tiny backing store, CSS upscaling, and one Safari gap

`image-rendering: pixelated` has shipped since Chrome 41 and Safari 10 ([BCD](https://github.com/mdn/browser-compat-data/blob/main/css/properties/image-rendering.json)). The awkward part is fractional scale: MDN says uneven pixels from non-integer device pixel ratios are "hard to solve completely" ([MDN, crisp pixel art](https://developer.mozilla.org/en-US/docs/Games/Techniques/Crisp_pixel_art_look)). Chrome offers `ResizeObserverEntry.devicePixelContentBoxSize` (84+) to read the exact device-pixel box; Safari does not ([BCD](https://github.com/mdn/browser-compat-data/blob/main/api/ResizeObserverEntry.json)), and its bug is still NEW as of 2026-09-30 with an unmerged patch linked ([WebKit bug 219005](https://bugs.webkit.org/show_bug.cgi?id=219005)). Current iPhones are an integer 3× except the minis at 2.88× (community: [Use Your Loaf](https://useyourloaf.com/blog/iphone-16-screen-sizes/)); Playwright's Pixel 7 and 8 profiles carry a DPR of 2.625 ([deviceDescriptorsSource.json](https://github.com/microsoft/playwright/blob/main/packages/isomorphic/deviceDescriptorsSource.json)), so Android needs the device-pixel box. iOS canvas limits are far away: a 16,777,216-pixel area cap and a total canvas memory budget reported as 224 MB on iOS 12 and 384 MB on iOS 15 (community: [pqina, area](https://pqina.nl/blog/canvas-area-exceeds-the-maximum-limit/); [pqina, memory](https://www.pqina.nl/blog/total-canvas-memory-use-exceeds-the-maximum-limit/)), against a 360 KB frame. One Safari hazard is on the present path: on an accelerated 2D canvas `putImageData` "forces a readback from the GPU" ([WebKit bug 234920](https://bugs.webkit.org/show_bug.cgi?id=234920)), so the notes suggest measuring it on a device against an unaccelerated context and a WebGL nearest-neighbour blit; no published comparison exists. OffscreenCanvas 2D with `transferControlToOffscreen()` has shipped since Safari 16.4 ([BCD](https://github.com/mdn/browser-compat-data/blob/main/api/OffscreenCanvas.json)), with worker-canvas bugs reported into 2024 ([bug 274300](https://lists.webkit.org/pipermail/webkit-unassigned/2024-May/1165880.html)).

### The CPU gap is wide, and compose time is not the binding constraint

Lighthouse's 4× CPU slowdown is defined as high-end desktop to mid-tier mobile ([Lighthouse throttling](https://github.com/GoogleChrome/lighthouse/blob/main/docs/throttling.md)). Alex Russell's 2026 analysis puts the 75th-percentile phone at a Galaxy A24-class device, low-end Android about **9×** slower single-core than a current iPhone and mid-tier more than **3.5×** slower (community, well regarded: [infrequently.org](https://infrequently.org/2025/11/performance-inequality-gap-2026/)). The project's own figure, quoted in the notes, is a compose step of about 3.6 ms at the 95th percentile under 4× throttle; from it the researchers infer 8–11 ms on a low-end phone, inside a 60 fps budget, so the binding constraints are the bake workers and memory. Suggested test devices in 2025 were the Galaxy A15 5G (low tier) and A54 5G (mid tier) (community: [Harry Roberts](https://conffab.com/elsewhere/low-and-mid-tier-mobile-for-the-real-world-2025/)).

### Every iPhone reports four cores; the pool, not the page, sets memory

WebKit's source clamps `navigator.hardwareConcurrency` to 4 on machines with fewer than 8 cores and 8 otherwise, to limit fingerprinting ([NavigatorBase.cpp](https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebCore/page/NavigatorBase.cpp)). iPhones have six cores, so every iPhone reports 4 whatever its RAM (inference from the source). A pool sized to that value holds **120–200 MB** on any iPhone at the site's 30–50 MB per bake worker, and 240–400 MB on an 8-core Android or iPad (arithmetic on the project's figure). WebKit engineers have called 20 workers "a bit excessive" in an app that hit the memory limit, and that app still died at 7 ([WebKit bug 256703](https://bugs.webkit.org/show_bug.cgi?id=256703)); one report measured about 70 MB per idle worker on an iPad ([WebKit bug 194268](https://bugs.webkit.org/show_bug.cgi?id=194268)), and another says a terminated worker that had received a transferred object never freed its memory, outcome unconfirmed ([WebKit bug 250569](https://bugs.webkit.org/show_bug.cgi?id=250569)). No game engine publishes phone pool guidance; Amazon's WebView guidance for low-resource devices says `hardwareConcurrency - 2`, or 2–4 for heavy workers ([Amazon](https://developer.amazon.com/docs/vega/2.0/webview-web-workers-best-practices)). The options the notes weigh: a fixed pool of 2 on phones (their suggestion, on the reasoning that iPhones have two performance cores and that extra workers on Android efficiency cores add heat and memory but little throughput), a pool tiered by `deviceMemory` where Chrome exposes it, or the full reported count. They favour a small long-lived pool over churn because of the leak report, and transferring `ArrayBuffer`s, the only zero-copy path without `SharedArrayBuffer`.

> **Measured in the iOS 26.5 Simulator (iPhone 17).** `navigator.hardwareConcurrency` reported 8, because the Simulator inherits the Mac's core count; this does not contradict the source-code reading that real iPhones report 4, but that reading is unconfirmed on a device. `navigator.deviceMemory` is `undefined`.

### iOS kills a tab near 1.5 GB, lower under pressure, and tells the page nothing

Apple publishes no per-device limit. The best primary statement is Simon Fraser's (2024-08-09): WebContent processes on iPhone have "a 'soft' limit of around 1.5GB", lower on iPhones with less RAM, enforced by jetsam according to system pressure ([WebKit bug 277848](https://bugs.webkit.org/show_bug.cgi?id=277848)). Community observations span a wide range: reloads near 3 GB on an iPhone 15 Pro and 1.5 GB on an iPhone 12 Pro ([same bug](https://bugs.webkit.org/show_bug.cgi?id=277848)), an iOS 26 log showing a 2048 MB limit with a kill at about 1.48 GB resident ([three.js forum](https://discourse.threejs.org/t/memory-limit-crash-on-ios-26/86978)), and Unity forum ceilings near 500 MiB for wasm heaps ([Unity Discussions](https://discussions.unity.com/t/webgl-deliver-for-all-platforms-including-iphones-930374/930374)). Worker heaps and JIT memory count against the one process limit ([WebKit bug 256703](https://bugs.webkit.org/show_bug.cgi?id=256703)), and the user-visible effect of a kill is a silent reload that can loop ([Apple Developer Forums 766309](https://developer.apple.com/forums/thread/766309)). Even four bake workers sit well under the soft limit on a foreground tab; the risk is low-RAM phones, memory pressure and background eviction. iOS gives a page no memory API: `deviceMemory`, `performance.memory` and `measureUserAgentSpecificMemory()` are all absent from Safari, and the last needs cross-origin isolation anyway ([BCD Navigator](https://github.com/mdn/browser-compat-data/blob/main/api/Navigator.json); [BCD Performance](https://github.com/mdn/browser-compat-data/blob/main/api/Performance.json)). On Android, `navigator.deviceMemory` changed in Chrome 147 to coarser buckets topping out at 8 ([Intent to Ship](https://groups.google.com/a/chromium.org/g/blink-dev/c/vXtAmrVZeDk)), and Chrome silently discards background tabs under pressure ([Chromium design doc](https://chromium.org/chromium-os/chromiumos-design-docs/tab-discarding-and-reloading)). The notes' budgets are inference with no sourced basis: at most about 300 MB in total on 4 GB phones and 500 MB on 6 GB and up, enforced by the game's own byte-counting of its chunk cache, with minimal state saved so a kill returns to the title screen.

### Heat is invisible to the page

The Compute Pressure API is desktop Chrome only (125+); Chrome for Android and Safari lack it ([BCD PressureObserver](https://github.com/mdn/browser-compat-data/blob/main/api/PressureObserver.json)). `navigator.getBattery()` exists in Chrome for Android and not in Safari ([BCD Navigator](https://github.com/mdn/browser-compat-data/blob/main/api/Navigator.json)). Published throttling figures come from native stress tests and GPU games, not web CPU loads: a Dimensity 9300 falling to 46% of peak within 15 minutes after throttling began at about 2 minutes ([GSMArena](https://www.gsmarena.com/the_dimensity_9300_throttles_after_2_minutes_in_stress_test-news-60717.php)), a Galaxy S26 Plus dropping from 113 to 80 fps in 10 minutes ([Android Authority](https://www.androidauthority.com/oneplus-15-update-benchmarks-3621249)), and iPhones dropping "considerably" over a 19-minute 3DMark run ([HotHardware](https://hothardware.com/news/ul-benchmarks-3dmark-wildlife-stress-test-benchmark-iphone-android)). Native games adapt from thermal APIs ([Unity Adaptive Performance](https://unity.com/blog/technology/higher-fidelity-and-smoother-frame-rates-with-adaptive-performance)); a page can only watch its own frame and bake times. The notes sketch, as inference, a controller that steps down (60 to 30 fps, pool 2 to 1, shorter bake distance) when same-sized bakes slow by 30–50% over the session baseline, with hysteresis before stepping up, plus stopping the loop entirely when a menu is open.

### Audio on iOS unlocks on a discrete tap and falls silent with the ringer by default

iOS has always required a user gesture to start an `AudioContext`, and WebKit engineers named `touchend`, not `touchstart`, as the unlocking event because a `touchstart` may begin a scroll ([WebKit bug 149367](https://bugs.webkit.org/show_bug.cgi?id=149367)); a `touchend` that follows a drag does not unlock ([bug 212117](https://lists.webkit.org/pipermail/webkit-unassigned/2020-May/925508.html)). A joystick drag will therefore never unlock audio; a discrete button tap must. Chrome starts a pre-gesture `AudioContext` suspended, wants `resume()` after a gesture, and recommends `click` ([Chrome autoplay](https://developer.chrome.com/blog/autoplay)). On the ringer switch, Apple's Jean-Yves Avenard: "By default the type is `ambient` and so audio will be muted if the phone is muted", and "Since iOS 17, you can set the audio session type to "playback"" ([WebKit bug 237322](https://bugs.webkit.org/show_bug.cgi?id=237322)). `navigator.audioSession.type` is a Safari-only API from 16.4 ([BCD](https://github.com/mdn/browser-compat-data/blob/main/api/AudioSession.json)); `playback` is exclusive and pauses the user's other audio, `ambient` mixes, and `transient` plays over and may duck ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/AudioSession/type)). The choice is thus between respecting the silent switch and the player's music (`ambient`) and being audible with the ringer off at the cost of stopping their music (`playback`). After a call, tab switch or screen-off the context enters `"interrupted"` and should be resumed ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/state)); reports describe contexts stuck there or "running" but silent ([WebKit bug 273511](https://bugs.webkit.org/show_bug.cgi?id=273511)), and CrazyGames tells developers to call `resume()` inside a `touchend` or `click` after any interruption ([CrazyGames](https://docs.crazygames.com/requirements/technical/)).

> **Measured in the iOS 26.5 Simulator (iPhone 17).** `typeof navigator.audioSession` is `object`. The ringer switch cannot be tested in a Simulator.

Only Chromium exposes network hints (`saveData`, `effectiveType`; [BCD](https://github.com/mdn/browser-compat-data/blob/main/api/NetworkInformation.json)), and `prefers-reduced-data` ships nowhere by default ([MDN](https://developer.mozilla.org/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-data)), so on iOS a tap gate is the only universal way to ask before a download; that same tap can unlock audio.

## Chromium automation covers the wiring; Safari's chrome needs the Simulator and a hand

### What the repository can already automate

Playwright (1.65.1, bundling Chromium 158 and WebKit 27.2, [release notes](https://github.com/microsoft/playwright/blob/main/docs/src/release-notes-js.md)) offers device profiles that set only viewport, screen, DPR, user agent, `isMobile` and `hasTouch` on a desktop browser build ([Playwright emulation](https://playwright.dev/docs/emulation)). Its touch API "is limited to emulating tap gestures" ([Touchscreen](https://playwright.dev/docs/api/class-touchscreen)), its gesture request was archived on 2025-09-04 ([playwright#2903](https://github.com/microsoft/playwright/issues/2903)), and its guide dispatches untrusted events that do "not set `Event.isTrusted`" ([touch events guide](https://playwright.dev/docs/touch-events)). Puppeteer has had per-finger `TouchHandle`s since 23.7.0 ([changelog](https://github.com/puppeteer/puppeteer/blob/main/packages/puppeteer-core/CHANGELOG.md)), and the repository already installs Puppeteer 25.0.4.

Local Puppeteer probes (headless Chrome 148, repository's own install) showed four things. Two simultaneous `touchStart` handles produced trusted `pointerdown` events with distinct ids (`isPrimary` true, then false), followed by per-finger moves and ups. Raw CDP `Input.dispatchTouchEvent` with `touchCancel` produced `pointercancel` for both pointers. `Emulation.setSafeAreaInsetsOverride` moved an `env()`-inset box as expected (left 59, bottom inset 21 in a 734×343 viewport). And opening a second page and calling `bringToFront()` produced real `hidden` and `visible` transitions, while `Page.setWebLifecycleState('frozen')` fired `blur`, `visibilitychange` and `freeze` but no return to visible. Under phone emulation `navigator.maxTouchPoints` was 1, so nothing should gate multi-touch on it. `screen.orientation.lock('landscape')` rejected with `NotSupportedError`.

The CDP surface behind this is documented: `Input.dispatchTouchEvent` (stable) and the experimental `synthesizePinchGesture`, which gives a cheap zoom check by asserting `visualViewport.scale === 1` afterwards ([CDP Input](https://chromedevtools.github.io/devtools-protocol/tot/Input/)); `setDeviceMetricsOverride` with `screenOrientation`, `setCPUThrottlingRate`, `setSafeAreaInsetsOverride` (first seen in the protocol on 2025-03-05) and a new `screenOrientationLockEmulation` parameter (2026-03-04) that intercepts `lock()` calls ([CDP Emulation](https://chromedevtools.github.io/devtools-protocol/tot/Emulation/); [protocol changelog](https://github.com/ChromeDevTools/devtools-protocol/blob/master/changelog.md)). Playwright's maintainers confirmed the safe-area call works through a CDP session and said of a built-in option, "No such plans" ([playwright#43283](https://github.com/microsoft/playwright/issues/43283)). Neither tool mocks gamepads; engines test them against fakes ([Phaser tests](https://github.com/phaserjs/phaser/tree/master/tests/input/gamepad)). Adding Playwright would buy WebKit and Firefox engine coverage and `toHaveScreenshot`, not better touch.

### What emulation cannot show

Playwright's WebKit is an automation build on the desktop OS, not the Safari app; its maintainers have closed requests for real mobile browsers ([playwright#1122](https://github.com/microsoft/playwright/issues/1122)) and for page-visibility control ([playwright#2286](https://github.com/microsoft/playwright/issues/2286)). The Simulator measurements above show the gap concretely: toolbar heights, the tab-bar case, Safari's own safe-area values and gesture behaviour appear in no device descriptor. Safari's own WebDriver on iOS simulates only "single-finger touches" and suppresses system gestures behind a glass pane (primary, written for iOS 13: [WebKit](https://webkit.org/blog/9395/webdriver-is-coming-to-safari-in-ios-13/)); Appium's web sessions on iOS call W3C Actions "currently unreliable" ([Appium XCUITest](https://appium.github.io/appium-xcuitest-driver/latest/guides/hybrid/)).

| Not caught by emulation | Cheapest check found |
|---|---|
| Safari toolbars, `dvh`, real safe-area values | iOS Simulator by hand; feed the logged numbers into unit tests and `setSafeAreaInsetsOverride` |
| Real pinch, double-tap, edge back-swipe, pull-to-refresh, home swipe | Real iPhone and Android phone by hand; Chromium proxy is `synthesizePinchGesture` |
| Orientation lock and fullscreen | One Android phone by hand; on iPhone assert the rotate prompt appears |
| Memory kills | An older real iPhone with Web Inspector attached during a long flight |
| Heat and real speed | A real device for 10 minutes or more with a frame-time readout; `emulateCPUThrottling(4)` as a rough proxy |
| Motion permission prompt, haptics, audio unlock and the ringer switch | Real devices by hand; unit-test the branches with stubs |
| Thumb reach, occlusion, latency | Real hands on one small and one large phone |

On this Mac the free stack is Xcode 27.2 with an iOS 26.5 runtime only (no iOS 27 runtime), `xcrun simctl` for boot, `openurl`, screenshot and video, and `safaridriver` for single-finger smoke tests; `simctl` has no rotate command and no privacy service for the web motion prompt; `adb` and Appium are not installed (local inspection). Playwright's Android support is "experimental" and needs ADB and Chrome 105+ ([Playwright Android](https://playwright.dev/docs/api/class-android)). BrowserStack's open-source programme offers free real-device testing for up to 5 users ([BrowserStack](https://www.browserstack.com/open-source)).

### Pixel-art controls are best pinned by hashing the frame

Playwright's `toHaveScreenshot` defaults suit DOM pages, not hard pixels: `scale: 'css'` downsamples a DPR-3 page to one pixel per CSS pixel, `threshold` defaults to 0.2, and baselines are per browser and platform because "Browser rendering can vary based on the host OS, version, settings, hardware, power source" ([PageAssertions](https://playwright.dev/docs/api/class-pageassertions); [visual comparisons](https://playwright.dev/docs/test-snapshots)). Its `animations: 'disabled'` stops CSS and Web Animations, not a rAF loop. The notes' recommendation, as inference, has two layers: controls drawn into the 400×225 buffer are pinned by hashing the RGBA buffer in `node --test`, as the repository's golden scripts already do, and a browser test reads the canvas back and compares the same hash; browser screenshots are kept for the DOM chrome (rotate prompt, mobile title menu) at DPR 1 and an integer multiple of 400×225, with per-OS baselines because browser-rendered IM Fell English differs between CoreText and FreeType. Engines structure their tests the same way: Phaser unit-tests `Pointer` and gamepad classes ([Phaser tests](https://github.com/phaserjs/phaser/tree/master/tests/input)), Excalibur splits pointer handling into separately tested receiver and dispatcher units with a custom visual matcher ([Excalibur specs](https://github.com/excaliburjs/Excalibur/tree/main/src/spec/vitest)), and KAPLAY keeps unit, integration and playtest folders under one Playwright config ([KAPLAY tests](https://github.com/kaplayjs/kaplay/tree/master/tests)). The shape those suggest is a thin DOM adapter that emits plain `{type, pointerId, x, y, t}` records into a pure reducer, with layout as a pure function of viewport, safe area and DPR. No open-source web game with a thorough end-to-end multi-touch suite was found.

## Shipped games offer two schemes, hide what is unusable and teach by doing

### Engines ship generic pads; the vocabulary comes from libraries and native games

Fantasy-console exports follow one recipe: detect touch, then add a fixed pad on the left and buttons on the right. PICO-8's web template gained "joystick & touch support... controls screen" in 0.1.12 ([Lexaloffle](https://www.lexaloffle.com/bbs/?pid=63593)) and draws its controls as bitmap panels around the square screen (community: [NerdyTeachers](https://nerdyteachers.com/PICO-8/Guide/EXPORT_HTML)); users reported touch buttons offset from their drawn positions inside itch.io iframes on some iPhones ([Lexaloffle](https://www.lexaloffle.com/bbs/?pid=63593)). GB Studio adds touch controls automatically with no customisation ([GB Studio](https://www.gbstudio.dev/docs/build/)). The lesson the notes draw is to compute hit areas from the same layout as the drawing and to give a visible way to turn the overlay off.

Native steering games are more instructive. Sky: Children of the Light offers a one-handed mode, in which the movement pad works from anywhere on screen, and two two-handed modes with a "Flip Sides" option ([Sky help](https://thatgamecompany.helpshift.com/hc/en/17-sky-children-of-the-light/section/116-controls-navigation)); launch reviews still called one-handed flight "ridiculously unreliable" (community: [Destructoid](https://www.destructoid.com/review-sky-children-of-the-light/)). Alto's Odyssey refused a second input altogether: "Any new touch inputs almost immediately made the game too hectic and frenzied" ([App Store story](https://apps.apple.com/us/story/id1343913400)). Larger games supply the standard option set that Microsoft cites as good practice: per-control size and position, opacity and scale sliders, preset layouts, and several schemes for the same action ([XAG 107](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/107)). Apple's guidance adds: hide movement controls until the player touches, "Don't leave controls visible that players can not use", keep the centre of the display clear, anchor controls to screen corners at constant physical size, and "Always include visible and tactile press states" that show "even when their finger is covering the control" ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/game-controls); [WWDC26 session 358](https://developer.apple.com/videos/play/wwdc2026/358/)). No authoritative source on pixel-art touch overlays was found. The transfer the notes make is inference: a pressed state that reads at the rim of the thumb (inverted ink and paper, a one-pixel offset, a reddened outer ring) in place of a glow, and controls placed in the side bars of a 16:9 frame where the screen is wider, or in a control deck below the frame in portrait.

Portal rules read as a QA checklist. Poki requires touch controls on phones and tablets and keyboard instructions on desktop, a 16:9 game that scales to fill, no scroll leaking to the parent page, and notes that players leave after 10 seconds of loading ([Poki](https://developers.poki.com/guide/requirements-quality)). CrazyGames forbids custom fullscreen buttons, requires legibility at 800×450 on mobile, wants new users in play within one click, and warns not to decide on mobile controls from `ontouchstart` or `maxTouchPoints` "since many laptops have touchscreens" ([CrazyGames gameplay](https://docs.crazygames.com/requirements/gameplay/); [technical](https://docs.crazygames.com/requirements/technical/)). The game's 400×225 frame is exactly the portals' 16:9.

### Teaching: evidence favours just-in-time prompts over a tutorial

A controlled study of over 45,000 players across three games found tutorials raised play time by up to 29% in the most complex game and made no significant difference in the two simpler ones; the authors conclude tutorials "may not be justified for games with mechanics that can be discovered through experimentation" (primary research, read as abstract: [Andersen et al., CHI 2012](https://grail.cs.washington.edu/projects/game-abtesting/chi2012/)). George Fan's GDC 2012 advice is to have players do, not read; get them to perform an action once; keep to "a maximum of eight words on the screen"; never pause play for a message; and show a tip only to players not already doing the thing (trade-press report: [Game Developer](https://gamedeveloper.com/design/gdc-2012-10-tutorial-tips-from-i-plants-vs-zombies-i-creator-george-fan)). Poki and CrazyGames both require onboarding that is visual, skippable and brief ([Poki](https://developers.poki.com/guide/requirements-quality); [CrazyGames quality](https://docs.crazygames.com/requirements/quality/)), and the Game Accessibility Guidelines ask for a reminder of controls available during play ([GAG](https://gameaccessibilityguidelines.com/full-list/)), which PICO-8 answers with a controls screen behind a menu button. The model the notes assemble is inference: define each lesson as an action to perform (steer, boost, land, leave), render its prompt for the input device in use, dismiss it when the action is detected, and keep a replayable controls card in the menu. Apple's context button makes the "land" prompt and the control one object on touch. No evidence was found on animated ghost-finger demonstrations against static glyphs.

### Prompts follow the device last used, not the device detected

Platform rules agree. Steam Deck review requires that "On-screen glyphs must match the inputs being used" and that keyboard glyphs not show when inactive ([Steamworks](https://partner.steamgames.com/doc/steamdeck/compat)); Xbox handheld guidance forbids prompts for inputs the device lacks ([Xbox](https://devdocs.xbox.com/build/gdk-and-engines/handheld/handheld-guidance.md)); XAG 107 requires prompts to reflect remaps ([XAG 107](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/107)). Apple splits the rule: for controllers, show the physical control's symbol; for touch buttons, show the action's own symbol and "Avoid using abstract shapes or controller-based naming like A, X, or R1" ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/game-controls)). On the web, capability queries give only a first guess: `pointer` tests the primary pointing device and hybrid devices match both `fine` and `coarse` ([MDN any-pointer](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/any-pointer)), and iPadOS sends a Mac user agent (community: [Apple Developer Forums](https://developer.apple.com/forums/thread/119186?page=2)). Gamepad brand cannot be read reliably, since `Gamepad.id` has no specified syntax ([MDN](https://developer.mozilla.org/docs/Web/API/Gamepad/id)), which favours positional glyphs and, incidentally, the project's rule against other properties' art. Keyboard labels for the user's layout come from `navigator.keyboard.getLayoutMap()`, which is experimental and of limited availability ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Keyboard/getLayoutMap)); binding by `KeyboardEvent.code` keeps WASD positional on AZERTY either way. The recipe the notes derive is inference: guess from `(pointer: coarse)`, then switch on real events (a `pointerdown` with `pointerType === 'touch'`, a `keydown`, a gamepad button), with a little hysteresis, and hide or dim the touch overlay while another device is active.

## Conclusion

The research changes the shape of the problem. "Locking the view" is not one feature with a fallback; it is two different products. On Android the game can own the screen from a tap: fullscreen, landscape lock, no toolbars, vibration. On iPhone it cannot own the screen at all in a tab, and the height it gets depends on how many tabs the visitor has open, enough to move the integer scale of a 400×225 frame from 4× to 3× on the same phone. Installing to the Home Screen is the only route to 5× and the full display on iPhone, yet it still does not lock rotation. The design therefore has to choose what the iPhone tab experience is, not how to approximate Android's.

Three constraints push in one direction: simplicity. The accessibility guidance asks for no required holds or simultaneous presses; the teaching evidence says a game with three or four verbs should not have a tutorial; and the best-regarded touch games either offer a one-thumb scheme or refuse a second input. Meanwhile the hard limits (four reported cores, no memory or thermal gauge, 30 fps in Low Power Mode) mean the phone build must budget for itself and measure itself. Most of this can be pinned with pure functions and the Puppeteer already in the repository. What cannot is the list below, and almost every item on it needs the same thing: a real iPhone and a real Android phone for an afternoon.
